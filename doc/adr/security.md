# Доверие и периметр безопасности

Документ описывает реализацию на коммите `5380b89` (ветка `master`, 2026-11-10), §4.2 и §4.5 — после TASK-28, §5.4 — после TASK-29, §4.3 и F3 — после TASK-36. Источник истины — код. Поиск адреса владельца для загрузки файла (`dialOwner`, TASK-27) в этот момент ещё дорабатывается, поэтому подробности о нём — в [`cache.md`](cache.md). Номера строк даны для коммита `5380b89`. Решения: A5, A11, A13, A16, A21, A22, A24, A28, A29, A31 в [`architecture.md`](../architecture.md), §7. Ревью: R01, R09, R11 в `doc/review-2026-11-09-fixed.md`.

## 1. Модель доверия

| Кто | Доверие | Чем подтверждается | Что может |
|---|---|---|---|
| **Участник pile**: устройство, знающее секрет S | полное (R11) | HMAC от K_auth, привязанный к TLS-каналу (§5) | читать весь журнал и писать в него, скачивать T1/T2/оригиналы любого участника, сообщать адреса пиров, переименовывать pile |
| **Посторонний в той же LAN** | нет | — | видеть mDNS-объявления, открыть TCP/TLS к портам pile и узнать ключ устройства (§4.4), видеть открытый HTTP-трафик показа, выдать себя за экран Cast |
| **Экран (renderer, ТВ)** | только на чтение медиа одного показа | токен в пути URL, HTTP без шифрования | на время показа получать T2 всех файлов хронологии и оригиналы видео |
| **Другое приложение на телефоне** | нет | — | подключиться к 127.0.0.1 и к портам pile, но без UI-токена или S получит 401 или обрыв соединения |
| **JS-слой приложения** | полное, это тот же процесс | UI-токен из `Mobile.token()` | всё UI API, в том числе получить приглашение с S |

Явно вне модели угроз:
- злонамеренный участник с действительным S и изменённым клиентом (R11). Например, он может заявить чужой `asset_id` с меньшим Lamport (A7), раздуть Lamport до 2^63−1 (A31), не передавать операции, подсунуть адреса пиров, создать сколько угодно Join на новые ключи;
- компрометация самого устройства: root, отладчик, извлечение данных приложения;
- атаки через интернет: синхронизации через интернет нет (§1.3), но см. находку F1;
- анонимность устройств в LAN (§4.4, F2).

### 2.1 Приглашение (QR)

`PILEUP:` + base32 (RFC 4648, без паддинга) от `0x01 ‖ CBOR[pile_id, secret, [addr…]]`, где `addr` — `netip.AddrPort.MarshalBinary` ([invite.go](../../core/invite/invite.go)). `Parse` требует: pile_id 1–255 байт, секрет ровно 32 байта, хотя бы один корректный адрес. Адреса — IP устройства без сотовых сетей (фильтр в Kotlin), global unicast без зоны (фильтр в Go, [mobile.go:116–133](../../core/mobile/mobile.go)), порт — порт pile.

**QR — это и пароль, и полное членство.** Подлинность QR не проверяется: если отсканировать чужой QR, устройство вступит в чужой pile.

### 2.2 Вход и создание pile

- **Создание:** `Create` записывает в журнал автора `Join` (seq 1, с proof), затем `PileCreate{name}` ([node.go:171](../../core/node/node.go)).
- **Вход по QR** (`Node.Join`): разобрать приглашение → отказ, если pile уже есть → `reach`: последовательно `peer.Dial` к адресам, найденным через mDNS (по тегу pile), затем к адресам из QR, каждый с таймаутом 5 с. Нужно полное взаимное доказательство членства (§5). Хранилище и `Join` создаются только после первого успешного соединения; этот адрес становится первым пиром и адресом владельца для ключа пригласившего (TASK-27) и записывается вместе с этим ключом (§4.5). При неверном S получаем `ErrUnreachable`, pile не создаётся (`TestInviteWithWrongSecretFailsToJoin`).
- Пригласивший узнаёт адрес вошедшего из `POST /announce` по уже аутентифицированному соединению (§4.2).

## 3. Целостность операций

- **Формат:** `envelope = CBOR [body_bytes, sig]`, `sig = ed25519(author_key, body_bytes)`, `body` — CBOR-map с ключами 1 pile_id, 2 author, 3 seq, 4 prev, 5 lamport, 6 wall_time, 8 type, 9 payload ([op.go:28–58, 97–100](../../core/crdt/op/op.go)). Подпись проверяется над **байтами тела в том виде, в каком они пришли** (`Decode`, op.go:118–135), поэтому каноничная сериализация не нужна. `ID = SHA-256(body_bytes)`. Хранится и пересылается исходный `raw`.
- **Декодирование:** дубликаты ключей CBOR запрещены. Операция неизвестного `type` хранится и пересылается, но в редьюсере не участвует. Ошибка payload известного типа отвергает операцию.
- **`Validator.Check`** перед записью ([validate.go:48–69](../../core/crdt/op/validate.go), вызывается из `store.apply`):

| Проверка | Ошибка |
|---|---|
| `pile_id` совпадает с pile хранилища (нельзя переиграть операцию в другом pile) | `ErrPile` |
| `seq`, `lamport` ≤ 2^63−1 (A31) | `ErrRange` |
| `seq = head.seq + 1`: без пропусков и буферизации | `ErrSeq` |
| `prev` пуст при seq 1, иначе равен `head.ID` | `ErrPrev` |
| `lamport > head.lamport` у того же автора | `ErrLamport` |
| seq 1 ⇔ `Join` с `proof = HMAC(K_auth, author)` (A5) | `ErrJoin` |

- **Членство в журнале** самодостаточно (A5): журнал автора принимается только с действительным Join. Таблица `members` только пополняется, исключения нет.
- **Форки** ([replica.go:313–341](../../core/replica/replica.go)): если пришла операция на уже занятый `(author, seq)` с другим ID или с `ErrPrev`, это `ErrFork`, локальный журнал не меняется. Тот же ID — повтор, его игнорируют. Форк виден, только если пир прислал расходящуюся операцию. При равной длине журналов вектор версий хешей не сравнивает (R09).
- **Пересылка через третий узел безопасна.** A получает операции B от C, и проверка не зависит от C: подпись B, цепочка `prev`, Join B с proof. C может только задержать или не прислать хвост журнала B. Подделать, переставить или выкинуть операцию из середины C не может: нужны ключ B и непрерывный префикс (`TestOpsRelayedByThirdNode`, `TestAnySingleByteChangeIsRejected`).
- Целостность blob: T1/T2/T3 берутся **только у владельца**. При соединении для загрузки проверяется, что ключ из TLS-сертификата собеседника равен `owner` ([blobs.go:244–270](../../core/node/blobs.go)). Хеша содержимого в CRDT нет, поэтому байтам верим как подлинным байтам владельца.

### 4.1 UI API (за UI-токеном)

`GET /health`; `GET|POST /piles`; `GET /piles/{id}/invite` (**возвращает S**); `POST /piles/join`; `GET|PUT /piles/{id}/selection`, `PUT /piles/{id}/selection/{asset}`; `GET /piles/{id}/timeline`; `GET /piles/{id}/blob/{asset}/{rev}/{tier}` (только T1/T2); `GET|POST|DELETE /piles/{id}/pins`, `GET /piles/{id}/pins/estimate`; `GET /screens`; `GET /diag`, `/diag/export`; `POST /reconnect`; `POST|GET|DELETE /show`, `POST /show/{next,prev,play,pause,goto}`. Заголовков CORS нет. Браузер на телефоне не может прислать `Authorization` без preflight, а preflight получает 401 (`TestHealthRejectsMissingOrWrongToken`, `TestNodeAPIRequiresToken`).

### 4.2 Порт pile (после рукопожатия §5)

| Маршрут | Что отдаёт или делает |
|---|---|
| `GET /vv` | вектор версий `{author → max seq}` |
| `POST /vv` | long-poll до 20 с: ответ, когда у сервера появилось то, чего нет в присланном VV |
| `GET /ops?author=&from=` | сырые операции автора с `seq ≥ from` (CBOR-seq) |
| `POST /announce?port=` | запоминает `RemoteAddr.IP:port` как пира вместе с ключом собеседника из TLS, если у адреса ещё нет ключа; адресом загрузки его файлов этот адрес не становится (A34). Начинает тянуть с него (если цикл к адресу ждёт паузы — прерывает её, A36) и отвечает JSON-списком `[{"key": <hex ключа>, "addr": "ip:port"}]` адресов других участников, у которых известен ключ, без адресов спрашивающего и самого отвечающего (§4.5) |
| `GET /blob/{asset}/{rev}/{1\|2\|3}` | только **свои** файлы: чужие и неизвестные — 404 ([blobs.go:272–305](../../core/node/blobs.go)). T1/T2 из кеша или рендера, T3 — оригинал с Range |

Сервер не проверяет, есть ли у ключа собеседника Join: **знать S достаточно**, чтобы получить весь журнал и любые оригиналы. Адреса из ответа `/announce` и из входящих announce сохраняются в `piles.json` вместе с ключом, который их назвал: участникам доверяем (§4.5).

### 4.3 Порт показа

Один маршрут: `GET /show/{token}/{asset}/{rev}/{tier}`. Токен верен и пара `(asset, rev)` есть в хронологии показа, тогда:
- `tier=2` — T2 (JPEG) **любого** файла хронологии pile, не только окна показа;
- `tier=3` — только для `KindVideo`: оригинал через `ServeOriginal` (свой или проксируется с владельца, с Range).

T1, T3 фото, другие ревизии, маршруты UI и порта pile здесь не отвечают (`TestRendererTokenOpensOnlyShowMedia`). Токен UI на этом порту не действует, токен показа не действует в UI. Порт pile открытым HTTP не отвечает. После `Stop` старый токен получает 403.

Если Cast-соединение оборвалось, порт показа закрывается, а хост переподключается к тому же адресу экрана с паузой 1, 2, 4 … 30 с, пока показ не остановлен (в состоянии показа — ошибка экрана `reconnecting`). После подключения порт открывается заново на локальном IP нового соединения и новом случайном порту с тем же токеном: адрес хоста мог смениться. Пока соединения нет, медиа показа по сети не отдаются (`TestShowReconnectsToScreenWithGrowingPauses`).

### 4.4 Что видит посторонний в LAN

- **mDNS** `_pileup._tcp` на каждый pile: имя экземпляра `pileup-<hex SHA-256(pubkey ‖ pile_id)[:8]>`, TXT ровно `pile=<hex SHA-256(pile_id)[:16]>`, порт pile в SRV ([discovery.go:51–82](../../core/node/discovery.go), A22). Сам pile_id и S в объявления не попадают. Но значения стабильны во времени и между сетями: видно, какие устройства состоят в одном pile.
- **Подключение к порту pile без секрета:** в TLS 1.3 сервер отправляет свой сертификат раньше, чем проверит клиента. Посторонний узнаёт **pubkey устройства**, ничего не доказывая. Сертификат легко опознать: самоподписанный ed25519, `NotBefore` 1970, `NotAfter` 9999.
- **Трафик показа** по HTTP: URL с токеном и сами JPEG/видео.
- **Поиск узлов по mDNS** (`Found`): узел подключается к любому адресу, объявленному с тегом его pile, но в `piles.json` адрес попадает только после успешного announce (A28).

### 4.5 Адреса участников (TASK-28, A35)

Адреса участников pile хранятся в `piles.json`, в обязательном поле `peers`: «адрес → ключ устройства, которое там отвечает». Адреса без ключа не бывает. `piles.json` без этого поля или с ключом не той длины не открывается. Это не членство (оно в журнале, §3) и не право доступа: каждое соединение всё равно проходит доказательство §5. Код — [`core/node/address.go`](../../core/node/address.go) и `announce`/`announced`/`learn` в [`node.go`](../../core/node/node.go).

| Источник | Что записывает | Перезаписывает ключ адреса? |
|---|---|---|
| наш announce на адрес прошёл (ключ из TLS) | адрес, ключ | да: это подтверждение |
| вход по приглашению (`reach`) | адрес принявшего, его ключ | да |
| входящий announce (ключ из TLS, адрес — IP соединения и объявленный порт) | адрес, ключ собеседника | нет, только если ключа ещё нет |
| список из ответа на announce | адрес, названный ключ | нет, только если ключа ещё нет |

- **Вытеснение.** Адрес удаляется из `peers`, а его цикл подключения отменяется, когда выполнены оба условия:
  1. участник с ключом этого адреса сейчас подключён (идёт синхронизация) по другому адресу;
  2. сам адрес не работает: его цикл последний раз завершился ошибкой или цикла нет.

  Цикл, у которого ещё не было неудачи, не вытесняется. Поэтому несколько рабочих адресов одного участника (IPv4 и IPv6, Wi-Fi и точка доступа) остаются. Проверка выполняется при подтверждении участника и после каждой неудачной попытки. Если вытесненный адрес был адресом загрузки участника, загрузка переходит на рабочий адрес.
- **Список в ответе на announce.** Адрес из списка не добавляется, если названный (или уже записанный) участник подключён по другому адресу, а сам адрес не работает. Поэтому старые адреса, которые помнят другие участники, не возвращаются. Входящий announce так не фильтруется: только он сообщает о переезде участника.
- **Собственный адрес.** Адрес, где наш announce получил наш же ключ, удаляется сразу. Записи списка с нашим ключом пропускаются. Announce от самого себя ответом `[]` ничего не добавляет.
- **Доверие.** Ключ в списке — утверждение участника, ему доверяем (R11). Неверный ключ может только помешать подключиться к неработающему адресу, пока тот не ответит. Адрес загрузки по-прежнему задаёт только подтверждение (A34).
- **Журнал диагностики** (`discovery`, поле peer — адрес; участник — `<имя> (<8 hex ключа>)`):
  - `new address of …, announced by the member | listed by <адрес> | confirmed by announce`;
  - `files of … are fetched from this address [instead of <адрес>]`;
  - `address now answers as … instead of …`;
  - `dropped address of …: it answers at <адрес>`;
  - `dropped address: this device answers here`;
  - `ignored address of … listed by <адрес>: it answers at <адрес>`;
  - `ignored own address listed by <адрес>`;
  - входящий announce: `connection` / `announce received from …`;
  - на адресе ответило другое устройство: `sync` / `sync: replica: another device answers at the address`.
- **Ограничения.**
  - mDNS-кандидаты до подтверждения не вытесняются: в `peers` их ещё нет, ключ неизвестен.
  - Пока участник ни по одному адресу не подключён, все его адреса остаются и опрашиваются (§5.4).

## 5. Соединение двух узлов

### 5.1 TLS ([peer.go:169–203](../../core/peer/peer.go))

- `MinVersion: TLS 1.3`, набор шифров по умолчанию в Go, без ALPN и SNI. Сессии не возобновляются: у клиента нет `ClientSessionCache`.
- Сертификат выпускается на **ключ устройства** при каждом `Dial` и каждом `NewListener`: самоподписанный x509, без Subject, серийный номер генерирует Go, срок 1970-01-01 … 9999-12-31 ([peer.go:179–189](../../core/peer/peer.go)).
- Взаимный TLS: `ClientAuth: RequireAnyClientCert`; `InsecureSkipVerify: true` (CA нет) и собственная проверка `VerifyConnection` на обеих сторонах ([peer.go:191–203](../../core/peer/peer.go)): ровно один сертификат, ключ ed25519, подпись сертификата проверяется его же ключом. Иначе `ErrCertificate`. Сроки действия не проверяются (A11). Владение ключом доказывает сообщение TLS 1.3 CertificateVerify, его проверяет стандартная библиотека.
- Ключ собеседника: `PeerCertificates[0].PublicKey` ([peer.go:75](../../core/peer/peer.go)). Его не сверяют с журналом. С ожидаемым ключом его сверяют в двух местах: при загрузке файла у владельца (§3) и в синхронизации. `replica.Pull` запоминает ключ первого соединения, и если после переподключения по тому же адресу ответило другое устройство, завершается с `ErrPeerChanged`. Тогда следующая попытка делает новый announce и записывает нового владельца адреса (§4.5, TASK-28).

### 5.2 Доказательство членства (A11)

```
Клиент (Dial)                                       Сервер (Listener)
  |--- TLS 1.3 ClientHello ------------------------------->|
  |<-- ServerHello, {Cert_S(ed25519), CertVerify} ---------|  клиент получает pub_S
  |--- {Cert_C, CertVerify, Finished} ------------------->|  сервер получает pub_C
  |   обе стороны: VerifyConnection, затем
  |   E = Exporter("EXPORTER-Channel-Binding", ctx=∅, 32)  (RFC 9266)
  |--- [len:1][pile_id:len][HMAC(K_auth, E ‖ pub_C):32] ->|  сервер: S = secrets(pile_id),
  |                                                       |  сравнение hmac.Equal; иначе закрыть
  |<-- [HMAC(K_auth, E ‖ pub_S):32] ----------------------|
  |   клиент: hmac.Equal, иначе ErrMembership
  |=== HTTP/1.1 внутри того же TLS ======================|
```

Код: [peer.go:70–122](../../core/peer/peer.go). Клиент проверяет `len(pile_id) ≤ 255` (`ErrPileID`). Сервер сначала читает 1 байт, потом `len + 32` байта, и знает только свой pile: `secrets(id)` = `(p.Secret, id == p.ID)` ([node.go:327–329](../../core/node/node.go)). При ошибке сервер закрывает TLS, ничего не ответив на уровне приложения. Рукопожатие выполняется лениво при первом `Read`/`Write`, поэтому на сервере его ограничивает `ReadHeaderTimeout` 20 с, а на клиенте — срок контекста `Dial`.

### 5.3 Почему MITM и ретрансляция не проходят

- Чтобы встать посередине, атакующий M ведёт две отдельные TLS-сессии, C↔M и M↔S, и у них **разные** значения exporter E₁ ≠ E₂. MAC клиента вычислен над E₁ и для сессии с сервером не годится. Чтобы вычислить MAC над E₂, нужен K_auth, то есть S.
- В MAC входит собственный pubkey доказывающего. Поэтому сервер без S не может вернуть клиенту его же MAC (`TestListenerReflectingDialerProofRejected`). Даже с украденным приватным ключом клиента M не проходит проверку (`TestRelayThroughMiddleman`, случай «stolen dialer key»).
- S по сети не передаётся. MAC привязан к одноразовому E, поэтому перехваченный MAC бесполезен и не даёт ничего для перебора: S — 256 случайных бит.
- TLS 1.2 отвергается обеими сторонами (`TestOnlyTLS13`). Поддельный сертификат (ключ A, подпись M) отвергается обеими сторонами с `ErrCertificate` (`TestForgedCertificateRejected`).

### 5.4 Исходы и что узнаёт каждая сторона

| Ситуация | Клиент видит | Сервер видит | Что узнали |
|---|---|---|---|
| оба знают S | успех | успех | ключи друг друга и то, что собеседник знает S |
| у клиента неверный S или на сервере нет этого pile | **EOF**: сервер закрыл соединение молча | `ErrMembership` | сервер: pub_C и запрошенный pile_id; клиент: pub_S |
| у сервера неверный S (самозванец по адресу из mDNS или старому адресу) | `ErrMembership` | — | самозванец: pub_C, pile_id, MAC, привязанный к E (бесполезен) |
| сертификат не ed25519, не самоподписан или их больше одного | `ErrCertificate` | `ErrCertificate` | pubkey из сертификата |

Повторы (A36, TASK-29; `connect` в [`node.go`](../../core/node/node.go), [`reconnect.go`](../../core/node/reconnect.go)):

- **Без конца.** Цикл подключения к адресу не завершается на сетевых и неоднозначных ошибках. Пауза перед n-м повтором — n×10 мс для n ≤ 100 (10 мс … 1 с, около 50 с в сумме), дальше 30 с. Удачный раунд синхронизации начинает отсчёт заново (`TestAmbiguousFailuresAreRetriedWithoutEnd`, `TestSeriesRestartsOnlyAfterSuccessfulSync`).
- **Что завершает цикл:**
  - `ErrCertificate` и `ErrMembership` (`TestAuthenticityErrorStopsSeriesWithoutPull`);
  - собственный адрес;
  - вытеснение (§4.5);
  - `Lost` для неподтверждённого mDNS-кандидата;
  - закрытие узла.
- **Отказ нам выглядит как EOF.** Поэтому он считается неоднозначной ошибкой и повторяется.
- **Паузу прерывает:**
  - входящий announce с адреса этого цикла (`TestIncomingAnnounceCutsThePause`);
  - `Node.Reconnect` — его вызывают UI-маршрут `POST /reconnect` при возврате приложения на передний план и проверка сетевых адресов устройства раз в 5 с, если набор адресов изменился (`TestReconnectRetriesNow`, `TestNetworkChangeReconnects`).

  После прерывания попытка идёт сразу, отсчёт пауз начинается заново. `Reconnect` также запускает новый цикл для каждого адреса из `peers`, у которого цикла нет: например, после `ErrMembership`.
- **Журнал** (`connection`, без pile):
  - `reconnect, <причина>: <n> waiting loops retried now, <m> loops started`;
  - `network addresses changed from [...] to [...]`.

## 6. От чего защищено и от чего нет

**Защищено (механизм):**
- посторонний в LAN не может читать или писать журнал и не может получить файлы с порта pile: нужно доказать знание S, MAC привязан к каналу;
- MITM, ретрансляция и отражение доказательства не проходят: TLS exporter, pubkey в MAC (§5.3);
- подделка или изменение чужой операции, в том числе при пересылке через третий узел: ed25519 над байтами тела плюс цепочка seq/prev (§3);
- перенос операции в другой pile: `pile_id` внутри подписанного тела;
- подмена файла другим участником при загрузке: TLS-ключ отвечающего должен совпасть с `owner` (§3);
- другие приложения на телефоне: UI-токен ≈130 бит, `127.0.0.1`; без S порт pile ничего не отдаёт;
- восстановление из бэкапа не продолжает старый журнал: `noBackupFilesDir`, ключ AndroidKeyStore не экспортируется (A21).

**Принятые ограничения:**
- утечка QR или строки приглашения означает бессрочное членство. Это касается фото экрана, пересылки через Share в мессенджер (секрет оказывается у мессенджера), скриншота (§7.2, A29);
- исключить участника, отозвать доступ, сменить S или ключ устройства нельзя (§1.3);
- участникам доверяем полностью (R11). Знающий S, даже без Join, может синхронизироваться и скачивать все оригиналы;
- показ и ТВ идут по открытому HTTP: внутри LAN можно перехватить URL с токеном и медиа (§7.2). ТВ (Cast) не аутентифицируется;
- форк с равной длиной журналов не обнаруживается (R09);
- в LAN видно присутствие устройств, их ключи и общие pile (§4.4);
- iOS не реализован: Keychain, NWListener/Bonjour и показ через AirPlay в коде отсутствуют, Swift-модуль — заглушка, есть только ключи Info.plist;
- подлинность QR не проверяется (§2.1).

## 7. Находки

Найдены чтением кода; тестами, кроме отмеченных, не подтверждались.

- **F1 (низкая).** Порт pile слушает **все интерфейсы** (`net.Listen("tcp", ":port")`, [node.go:307](../../core/node/node.go)), в том числе сотовую сеть и VPN. Сотовые адреса исключены только из приглашения. При глобальном IPv6 на сотовой сети порт может быть доступен из интернета, если оператор не фильтрует входящие. Данных без S не отдать, но открыты pubkey устройства (§4.4) и затраты на TLS-рукопожатия (DoS).
- **F2 (низкая, приватность).** Посторонний получает долговременный pubkey устройства, просто подключившись к порту pile, а тег pile и имя экземпляра в mDNS стабильны. Значит, устройства можно отслеживать между сетями и видеть, кто с кем в одном pile. Частично заложено в §7.1 п.7.
- **F3 (низкая, исправлено в TASK-36).** Раньше после обрыва Cast-соединения `drive` завершался ([renderer.go:162–164](../../core/show/renderer.go)), а HTTP-сервер показа и токен оставались действительными до `Host.Stop`/`Start`/`Close` ([session.go:240–247](../../core/show/session.go)), даже если пользователь так и не нажимал «стоп». Теперь на время обрыва порт закрыт, хост сам переподключается, а токен действует, пока показ не остановлен (§4.3).
- **F4 (низкая–средняя).** Экраны берутся из mDNS без аутентификации, а Cast-TLS идёт с `InsecureSkipVerify` ([cast.go:85](../../core/cast/cast.go)). Посторонний в LAN может объявить поддельный `_googlecast._tcp`. Если пользователь выберет его, атакующий получит URL с токеном, а по нему — T2 всего pile и оригиналы видео на время показа. Это активная атака, а не только перехват из §7.2.
- **F5 (информационная).** Токен показа открывает T2 **всей** хронологии, а не только текущего окна, как читается в A24. Постороннему нужно ещё знать `(asset_id, revision)`. `asset_id = SHA-256(pubkey ‖ "image:<_ID>")` предсказуем, если известен pubkey (F2); `revision = SHA-256(BE64 DATE_MODIFIED)` перебирается с трудом. Перебор не проверялся.
- **F6 (низкая).** Seed ключа устройства запечатан AndroidKeyStore, а секрет S, который даёт членство, лежит в `piles.json` открытым текстом ([node.go:532–542](../../core/node/node.go)). Его защищает только песочница приложения. Защита асимметрична: S ценнее ключа устройства.
- **F7 (низкая, живучесть).** `ErrFork` прерывает `Pull` с этим пиром ([replica.go:276–289, 313–337](../../core/replica/replica.go)) и не относится к ошибкам подлинности. Поэтому попытки повторяются без конца (после линейного участка раз в 30 с, §5.4). Один форкнутый автор ухудшает синхронизацию с таким пиром для всех авторов. Операции других авторов в каждой попытке применяются, но long-poll не работает.
- **F8 (низкая, DoS).** Посторонний может объявить в mDNS много сервисов с тегом чужого pile. Каждый `Found` запускает серию подключений, а самозванец, который молча закрывает соединение, даёт EOF. Это неоднозначная ошибка, она повторяется, пока не придёт `Lost` (после линейного участка раз в 30 с на кандидата). `Lost` отменяет неподтверждённого кандидата, но объявления дешёвые.
- **F9 (информационная).** Один K_auth используется в двух HMAC без метки домена: для Join, где вход 32 байта (pubkey), и для канала, где вход 64 байта (E ‖ pubkey). Из-за разной длины входов смешать их сейчас нельзя. Ключ устройства тоже общий для TLS CertificateVerify и подписей операций. Путаницы протоколов нет: TLS 1.3 подписывает с префиксом из 64 пробелов и контекстной строки, а тело операции — CBOR-map.
