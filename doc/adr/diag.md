# Журнал диагностики

Код: [`core/diag`](../../core/diag/diag.go), создание и запись запуска — [`core/node/node.go`](../../core/node/node.go) `Open`, HTTP — [`core/httpapi/diag.go`](../../core/httpapi/diag.go), падения и натив — [`core/mobile/mobile.go`](../../core/mobile/mobile.go), приложение — [`app/src/report.ts`](../../app/src/report.ts), [`app/src/screens/Log.tsx`](../../app/src/screens/Log.tsx). Решения A23, A60.

## Модель

- Журнал один на узел, кольцо из 1000 событий в памяти. Событие: время, вид, pile (байты id или пусто), peer (адрес, hex-ключ участника или имя экрана), сообщение на английском, счётчик.
- Виды: `discovery`, `connection`, `sync`, `timeout`, `renderer`, `media`, `app` (запуск, ошибки приложения и записи журнала), `crash` (аварийное завершение прошлого запуска). Подписи видов в приложении — по-русски.
- Повтор (тот же вид, pile, peer, текст) склеивается: счётчик растёт, событие поднимается наверх, время — последнего повтора. Ошибки таймаута (`context.DeadlineExceeded`, `net.Error.Timeout`) записываются видом `timeout`.
- `diag.New(size)` — журнал только в памяти (тесты пакетов), `diag.Open(dir, size)` — с файлом.

## Хранение на диске

- `<dir>/diag.log`: по строке JSON на запись `{"time","kind","pile","peer","message","count"}`, `count` — накопленный счётчик серии. Когда файл достигает 256 КиБ, он переименовывается в `diag.log.1` (прежний `.1` теряется), начинается новый. На диске не больше ~512 КиБ.
- Запись идёт сразу при `Add`, под мьютексом журнала, без fsync: после падения процесса строки уже в файле. Повтор серии пишется не чаще раза в минуту; остаток счётчика дописывается при `Close`. После аварийного завершения счётчик частой серии может быть занижен (последняя минута).
- `Open` читает `.1` и `diag.log` (каждый не больше 512 КиБ), для каждой серии берёт последнюю строку, сортирует по времени и оставляет последние 1000. Нечитаемые строки (обрыв при падении) пропускаются; если файл не кончается переводом строки, он дописывается перед новой записью.
- Ошибка открытия или записи (нет места, нет каталога, нет прав) не ошибка работы: в память добавляется событие `app` «diagnostics are not saved to disk: <ошибка>», файл закрывается, следующая попытка — не раньше чем через минуту. `Open` ошибок не возвращает. Тесты: `TestUnwritableDirKeepsEventsInMemory`, `TestFullDiskKeepsEventsInMemory` (`/dev/full`).
- `Node.Close` закрывает журнал; события после этого остаются только в памяти.

## Запуск и аварийное завершение

- `node.Open` первым событием пишет `app` «Pileup <версия> <платформа> started» (повторные запуски одной версии склеиваются: время — последнего запуска).
- `mobile.Start` до открытия узла открывает `<dir>/crash.txt` (дописывание) и вызывает `debug.SetCrashOutput`: необработанная паника и fatal error рантайма Go печатаются туда в дополнение к stderr. Непустой файл при следующем успешном `Start` даёт событие `crash` «previous run crashed at <время изменения файла>: <первые 4 КиБ трассы>», после чего файл очищается. Если `Start` не удался, след остаётся до следующего удачного. Паника внутри HTTP-обработчика перехватывается `net/http` и аварией не считается. Тест: `TestGoCrashIsInLogAfterNextStart` (дочерний процесс паникует, следующий `Start` видит след в `GET /diag` и экспорте, повторный запуск его не дублирует).

## Вход для чужих ошибок

- `POST /diag {"kind","message"}` за UI-токеном: вид — один из видов выше, кроме `crash`; пустое сообщение или другой вид — 400 `bad_request`; ответ 204. Pile и peer не передаются.
- `mobile.Report(kind, message string)` — для Kotlin и Swift. Без возвращаемого значения, без колбэков, потокобезопасна, не ждёт `Start`/`Stop`. Вызывать можно в любой момент: пока ядро работает — событие сразу в журнале; до `Start` и после `Stop` — копится в памяти процесса (первые 100) со временем вызова и попадает в журнал при следующем `Start` с этим временем, а не со временем запуска. Виды: `discovery` (NSD и Bonjour), `media` (медиатека), `app` (прочее). Неизвестный вид записывается как есть.
- Приложение (`app/src/report.ts`): `connect()` назначает приёмником новый `Api` (после перезапуска ядра ошибки идут на новый порт с новым токеном) и ставит глобальный обработчик `ErrorUtils`, сохраняя прежний. Нефатальная ошибка уходит в журнал и передаётся прежнему обработчику сразу; фатальная — прежнему обработчику после отправки, но не позже чем через 1 с. В release включается трекер необработанных отклонений Hermes. `Boundary.componentDidCatch` отправляет ошибку со стеком компонентов. Сбой отправки молча игнорируется.
- Android: ошибки `NsdManager` (регистрация, снятие, поиск, остановка поиска, resolve) — `discovery` «nsd: <что> failed, error <код>»; `MediaStore` без курсора — `media`.

## Секреты

- Из любого сообщения вырезаются строки приглашения (`PILEUP:` и base32, без учёта регистра) — в них секрет pile. Из сообщений `POST /diag` и `mobile.Report` вырезается текущий UI-токен. Сообщение длиннее 4 КиБ обрезается.

## Чтение

- `GET /diag` — события, новые сверху; `GET /diag/export` — text/plain: заголовок, пустая строка, события по порядку (`<время UTC> <вид> [pile=<hex>] [peer=…] [xN] <сообщение>`).
- Заголовок: `Pileup <версия> <платформа>; device <8 hex ключа>; <время UTC> (UTC±hh:mm)`, затем строка на pile: `pile «<имя>» <8 hex id>: <имя> (<8 hex>) <платформа> <версия> online | offline since <время> | never seen[, <класс ошибки>]; …`.
- В обоих ответах peer, равный hex-ключу участника любого pile, заменяется на `<имя> (<8 hex>)` (`TestDiagExportStartsWithContext`).

## Ограничения

- Журнал не реплицируется: причина отказа владельца видна только в журнале его телефона.
- Падения нативного кода (Kotlin, Swift, JNI) и фатальные ошибки JS, после которых процесс гибнет раньше отправки, следа не оставляют. Версии ОС в журнале нет (платформа приходит как `android`/`ios`).
- Имени pile в строках событий нет — только id; соответствие — по заголовку экспорта.
