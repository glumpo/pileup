Ревьюер: линза V. Код: `master` @ 3b84d31. Эксперименты лежат в `/root/prog/pileup-wt/review-video` (worktree, ничего не коммитилось):

- `core/show/zz_video_review_test.go` — неподдерживаемый кодек, нечитаемый оригинал (плюс 6 строк в `core/show/helpers_test.go` worktree: флаг «оригинал только в iCloud» у фейковой медиатеки).

Запуск: `cd /root/prog/pileup-wt/review-video/core && go test -p 2 ./node ./show -run TestReview -v -count=1`.

## Путь байтов и управления (как устроено сейчас)

```
ТВ (Default Media Receiver)
  │ GET /show/{token}/{asset}/{rev}/3  + Range          core/show/renderer.go:352 serve
  ▼
хост: show-порт (http, без WriteTimeout)                 renderer.go:347
  │ node.ServeOriginal                                    core/node/blobs.go:356
  │   владелец = хост → original{} → ServeContent         blobs.go:370
  │   иначе relayOriginal: Range/If-Range/If-None-Match → blobs.go:382–414
  ▼   (таймауты A41: 20 с до заголовков, 10 с простоя чтения у владельца)
peer-маршрут владельца GET /blob/{a}/{r}/3 (TLS 1.3 + HMAC, HTTP/1.1)  blobs.go:321
  │ original.Read: ReadOriginal(id, pos, 1 МиБ) на каждый МиБ          blobs.go:442
  ▼
gomobile → Kotlin Renditions.readOriginal: openFileDescriptor + ByteBuffer + copyOf  Renditions.kt:36–43
```

Управление: пульт опрашивает `GET /show` раз в 1 с (`Remote.tsx:45`). Команды play/pause идут в `session.control` (`session.go:166`), затем в `drive` (`renderer.go:416`), который последовательно шлёт LOAD/PLAY/PAUSE и ждёт ответа ресивера. Seek с пульта не предусмотрен: в `cast.Media` нет `currentTime` (`cast.go:41–59`).

### Замеры на x86 (Go-часть с фейковым провайдером; два узла и клиент в одном процессе, loopback)

| Что | Результат |
|---|---|
| Поток владелец → хост (TLS) → клиент, 256 МиБ, ReadOriginal без задержки | 204–336 МБ/с (1,6–2,7 Гбит/с), 256 вызовов ReadOriginal |
| То же, ReadOriginal с задержкой 5 мс на вызов (имитация `openFileDescriptor` и чтения на телефоне) | 102–122 МБ/с (0,8–1 Гбит/с) |
| CPU на весь путь | 5,9–7,3 мс CPU на МиБ (владелец + хост + клиент) |
| Аллокации Go | 1,0 МиБ на МиБ потока (кусок из ReadOriginal), ~65 циклов GC на 256 МиБ |
| 20 Range-запросов `bytes=N-` с обрывом после 256 КиБ (модель seek) | первый 256 КиБ за 4–10 мс; владелец прочитал 41 МиБ ради 5 МиБ (буферы TCP в полёте); горутины 29 → 24, утечек нет |
| `Range: bytes=0-1` | владелец читает целый 1 МиБ |
| Клиент не читает 6 с при idle-таймауте 2 с (пауза на ТВ) | соединение живо, чтение продолжается — A41 держит |

Оценка для телефона (в 5–10 раз медленнее x86): Go-часть даёт сотни Мбит/с. CPU — порядка 10–20 % одного ядра на 50 Мбит/с, суммарно у владельца и хоста. Нативная часть (fd на каждый кусок, 4–5 копий на кусок: `ByteBuffer` → `copyOf` → `GetByteArrayElements`/`memcpy` в gomobile → `C.GoBytes`) добавляет единицы миллисекунд на МиБ. **Владелец и Go-путь узким местом не являются.** Узкое место — эфир Wi-Fi (V1), а видимые пользователю проблемы — в управлении и диагностике (V2–V6).

Справочные битрейты: iPhone 4K30 HEVC ≈ 23 Мбит/с, 4K60 HEVC ≈ 50 Мбит/с, 4K60 H.264 («Наиболее совместимый») ≈ 60 Мбит/с. Android 4K30 H.264 ≈ 40–50 Мбит/с, 4K60 — 60–80 Мбит/с. 1080p30 — 6–17 Мбит/с.

## Находки (по убыванию важности)

### V1. Видео чужого владельца проходит по эфиру Wi-Fi четыре раза; на 4K и слабом Wi-Fi это буферизация

- **Критерий:** отзывчивость (видео без подгрузки). **Важность:** высокая: это главный источник видимого торможения 4K, и в коде нет ни смягчения, ни диагностики (V4).
- **Сценарий:** Боря снял 4K60 на Android (~70 Мбит/с). Хост — телефон Ани, ТВ в той же сети. Видео идёт рывками или постоянно буферизуется, фото при этом листаются нормально.
- **Где:** `core/node/blobs.go:382–414` (relay), `core/show/renderer.go:367–369`, принцип «renderer общается только с host'ом» (architecture.md §0), риск 3 в §9.
- **Что происходит:** при одной точке доступа каждый байт проходит владелец → AP → хост → AP → ТВ, то есть четыре передачи по общему эфиру. 70 Мбит/с видео занимают ~280 Мбит/с эфира, а реальная суммарная пропускная способность бытовой AP на 5 ГГц с телефонами и ТВ — 150–400 Мбит/с. На 2,4 ГГц (40–80 Мбит/с) не пройдёт даже 4K30. Хотспот одного из телефонов даёт 50–150 Мбит/с. Если хост — сам хотспот, переходов два; если хотспот — третий телефон, их снова четыре. Когда владелец видео — сам хост, переходов два (host → AP → ТВ). Буфер ТВ при прогрессивной загрузке — секунды–десятки секунд, поэтому недобор полосы проявляется как «играет, встало, крутится».
- **Когда проявится:** 4K30 H.264 и выше от не-хоста — на 2,4 ГГц и хотспоте почти наверняка. 4K60 — вероятно и на средней 5 ГГц AP, особенно при 3–4 активных телефонах и ТВ далеко от AP. 1080p — нет.
- **Уверенность:** гипотеза (расчёт по эфиру). Go-путь проверен замером: он не ограничивает поток (см. таблицу).
- **Класс:** архитектурная проблема. Варианты:
  1. **Замерить и честно показать** (V4: битрейт видео против фактической скорости и подсказка «Wi-Fi не успевает: видео 4K ≈ 70 Мбит/с, сеть даёт ≈ 25. Запустите показ с телефона Бори или подойдите ближе к роутеру»). Цена малая, риска нет, проблема остаётся, но становится понятной.
  2. **Прямой поток владелец → ТВ.** Хост в LOAD отдаёт URL владельца: владелец открывает на время показа отдельный HTTP-порт с одноразовым токеном, который хост получает у него по peer-каналу. Это убирает два из четырёх переходов. Цена средняя: новый маршрут, токены, перенос логики «502 → постер» (сейчас она смотрит на ответ хоста, `renderer.go:370`) на `MEDIA_STATUS`/LOAD_FAILED. Риски: нарушается принцип §0, у владельца появляется открытый порт без TLS (как сейчас у хоста), ТВ должен видеть владельца (клиентская изоляция гостевых сетей). Отдельно не проверено, что DMR корректно ходит на другой адрес, чем для фото.
  3. Перекодирование — исключено §1.3.
  
  **Рекомендация:** сейчас вариант 1 (вместе с V4). В TASK-20 замерить 4K30/4K60 с Android и iPhone на 5 ГГц, 2,4 ГГц и хотспоте. Вариант 2 делать, только если 4K60 на нормальной 5 ГГц AP заметно буферизуется.
- **Объём:** вариант 1 — в рамках V4; вариант 2 — 3–5 дней.

### V2. Неподдерживаемый экраном кодек: бесконечный LOAD раз в секунду, на ТВ заставка или чёрный экран, причины нет

- **Критерий:** понятность проблем, надёжность. **Важность:** высокая: iPhone по умолчанию пишет HEVC (часто с HDR/Dolby Vision), и §2.3 прямо требует плашку вместо чёрного экрана.
- **Сценарий:** на экране видео с iPhone в HEVC HDR. ТВ (Chromecast HD, старый Chromecast, ТВ без HEVC) не может его декодировать. На ТВ мигает заставка Cast или чёрный экран, пульт почти всё время пишет «Экран не смог воспроизвести видео. Попробуйте следующий файл.». Ресивер получает LOAD этого же видео каждую секунду, и владелец каждый раз заново отдаёт начало файла.
- **Где:** `core/show/renderer.go:461–462`: `status` при IDLE/ERROR возвращает false, и через `reload` (1 с) `loaded` сбрасывается. В `renderer.go:439–443` идёт повторный LOAD. `session.go`: `videoDown` при этом не ставится. `Remote.tsx:15` — общий текст. `cast.go:41–59`: `detailedErrorCode` из MEDIA_STATUS и сообщения `ERROR` не разбираются. Повтор закреплён тестом `core/show/reload_test.go:78` (`TestLoadEndingInPlaybackErrorIsRepeated`): он задуман для «поздней» ошибки, но на постоянную ошибку кодека работает так же.
- **Уверенность:** цикл **воспроизведён**: `TestReviewUnsupportedVideoIsReloadedForever` — «in 10 s: 10 LOADs of the HEVC video, owner ReadOriginal calls 30; remote polls: 196 with playback_failed, 1 without error». Что именно рисует DMR при ошибке декодера — гипотеза, нужен ТВ.
- **Класс:** баг в логике. Красный тест: ресивер всегда отвечает IDLE/ERROR на видео → не больше N LOAD за 10 с (например, 2–3); затем экран получает LOAD постера (T2, `image/jpeg`); в состоянии показа `video_unavailable` с причиной `unsupported`, а не `playback_failed`. Правка: после ошибки воспроизведения повторить LOAD один раз (сохраняется смысл A32 для «поздней» ошибки). При второй ошибке на том же файле поставить `videoDown` с причиной «экран не воспроизводит», показать постер и написать на пульте «Экран не воспроизводит это видео (вероятно, HEVC/HDR с iPhone). Посмотрите его на телефоне или переходите к следующему». Если известен `Codec` (iOS может заполнять, см. требования к TASK-43), подставить его в текст. «Воспроизвести» даёт ручную повторную попытку.
- **Объём:** 0,5–1 день.

### V3. Владелец не может прочитать оригинал (только в iCloud, файл удалён, доступ отозван): 500 вместо 502, бесконечный LOAD, причина теряется

- **Критерий:** понятность проблем. **Важность:** высокая для iPhone (опция «Оптимизировать хранилище» включена у многих), средняя для Android (файл удалён из галереи после выбора, частичный доступ Android 14).
- **Сценарий:** видео Ани лежит только в iCloud. На ТВ заставка, пульт пишет «Экран не смог открыть этот файл. Попробуйте следующий.», показ каждую секунду повторяет LOAD. В журнале хоста — только `LOAD_FAILED code=905`. Настоящая причина («оригинал только в iCloud») есть лишь в теле ответа 500, которое уходит на ТВ, и в журнале владельца.
- **Где:** `core/node/blobs.go:331–335, 348–349`: ошибка `OriginalSize`/`ReadOriginal` у владельца даёт `http.Error(…, 500)`. `blobs.go:406–412`: relay передаёт 500 экрану как есть. `core/show/renderer.go:370`: постер и подсказка включаются только на 502. Для собственного видео хоста (`blobs.go:370–374`, 502) `unavailable` не вызывается из-за `a.Owner != s.self`: снова цикл.
- **Уверенность:** **воспроизведено**: `TestReviewICloudOnlyVideo` — «in 5 s: 5 LOADs, owner OriginalSize calls 5; state: video_unavailable=false error="load_failed: cast: LOAD_FAILED reason=\"\" code=905" hints=0». В журнале хоста про причину ничего.
- **Класс:** баг в логике плюс маленький контракт. Красный тест — ровно этот: оригинал не читается → не больше 1–2 LOAD, экран получает постер, в состоянии причина `original_unavailable`, в журнале хоста текст владельца. Правка:
  1. У владельца ошибка чтения оригинала отдаётся отдельным кодом (например, 409/422 с `{"reason": "not_local" | "unreadable"}`).
  2. Relay не транслирует 4xx/5xx владельца экрану как поток, а отвечает 502 и сохраняет причину.
  3. `serve` ставит `videoDown` с этой причиной, в том числе для собственного видео хоста.
  4. Пульт пишет «Видео Ани есть только в iCloud — откройте его в «Фото» на iPhone Ани, чтобы скачать, или переходите к следующему».
- **Объём:** 1 день (ядро и пульт), плюс соглашение об ошибке с нативом (см. требования к TASK-43).

### V4. Буферизация не видна ни на пульте, ни в журнале

- **Критерий:** понятность проблем. **Важность:** средняя–высокая: при V1 это единственное, что объяснит пользователю «тормозит», а сейчас «грузится» не отличить от «зависло».
- **Сценарий:** видео встало, на ТВ крутится индикатор (если DMR его рисует). На пульте «Пауза», как будто всё играет. В экспорте журнала ничего: ни буферизаций, ни скорости.
- **Где:** `core/show/session.go:226`: `BUFFERING` сворачивается в `Playing`. `cast.go:55–59`: из MEDIA_STATUS берутся только `playerState` и `idleReason`, без `currentTime` и `media.duration`. `Remote.tsx:157–162`: одна кнопка. `blobs.go:412–413`: relay пишет в журнал только тишину владельца, без скорости.
- **Уверенность:** подтверждено чтением кода.
- **Класс:** простая правка плюс небольшой новый сигнал:
  1. `State.Buffering` и на пульте строка «Видео подгружается…».
  2. Если буферизация повторяется или длится больше ~2 с, хост пишет в журнал и показывает на пульте «Wi-Fi не успевает за видео: нужно ≈ X Мбит/с, идёт ≈ Y». X хост знает без чтения файла: `size_bytes × 8 / duration_ms`, оба поля есть в AssetMeta. Y — байты relay за последние секунды.
  
  Это же закрывает диагностику V1 и V7.
- **Объём:** 0,5–1 день.

### V5. Источник видео засыпает или уходит в фон: у владельца нет keep-awake и баннера раздачи, а видео, в отличие от фото, не кешируется

- **Критерий:** надёжность. **Важность:** средняя–высокая: в опорном сценарии телефоны участников лежат на столе, автоблокировка — 30 с–2 мин.
- **Сценарий:** 3-минутное видео с iPhone Ани. Через ~30 с у iPhone гаснет экран, приложение приостанавливается. ТВ доигрывает буфер, затем видео замирает. Ещё ~10 с relay ждёт (A41), следующий Range ещё ~5 с ждёт dial (`dialTimeout`). Только потом на ТВ постер, а на пульте «Видео недоступно…». С Android при уходе на домашний экран на Android 14+ процесс без foreground service может быть заморожен (cached apps freezer) с тем же итогом. При простом погасании экрана Android держится дольше, до Doze.
- **Где:** keep-awake есть только на пульте (`Remote.tsx:40`, A47); баннер §6.3 «Не блокируйте экран, идёт раздача» не реализован (поиск по `app/src` пуст). В API ядра нет признака «сейчас отдаю оригинал». У `original`/`serveBlob` (`blobs.go:321–354`) нет счётчика активных потоков.
- **Уверенность:** подтверждено чтением кода; поведение iOS и Android-freezer — гипотеза, нужно устройство.
- **Класс:** архитектурная проблема (малая). Варианты:
  1. Ядро считает активные T3-потоки и отдаёт `serving` в `GET /health` или `GET /piles`. UI держит экран включённым (`activateKeepAwakeAsync`) и показывает баннер, пока `serving` > 0 и ещё ~30 с после. Цена малая, работает на обеих платформах, пока приложение на экране.
  2. Плюс на iOS `beginBackgroundTask` при уходе в фон во время потока: ~30 с дожить. По истечении ядро должно закрыть сокеты (TASK-44), тогда хост получит RST сразу, и постер появится через ~1 с, а не через ~15–20 с.
  3. Foreground service на Android только на время раздачи. A47 его осознанно не берёт, и при варианте 1 он не нужен.
  
  **Рекомендация:** 1 + 2.
- **Объём:** 1 день плюс проверка на устройствах.

### V6. После любого восстановления видео начинается сначала; короткий сбой оставляет постер до ручного «Воспроизвести»

- **Критерий:** надёжность, отзывчивость. **Важность:** средняя: на неидеальном Wi-Fi это «посмотрели 2 минуты, моргнуло — смотрим заново с нуля».
- **Сценарий:**
  - (а) Обрыв Cast (A44): после переподключения LOAD текущего файла, видео с 0:00.
  - (б) ТВ сделал новый Range-запрос в момент, когда владелец секунду не отвечал (роуминг, power-save). Dial не прошёл, 502, `videoDown` до конца слайда (`renderer.go:370`, `session.go:200–211`). Авто-возврата нет. «Воспроизвести» перезапускает с начала (`session.go:174–181`).
  - (в) V2/V3 после исправления — то же.
- **Где:** `cast.go:41–59, 127–137`: нет `currentTime` ни в статусе, ни в LOAD. `session.go:148–164`. `renderer.go:416–473`.
- **Уверенность:** подтверждено чтением кода; (а) записано в `architecture-review.md` §1а как ограничение.
- **Класс:** простая правка с тестом:
  1. Разбирать `currentTime` из MEDIA_STATUS и хранить его в сессии по ключу файла.
  2. При повторном LOAD того же видео (переподключение, ручной play после `videoDown`, повтор после ошибки) передавать `"currentTime"` в LOAD.
  3. Для (б) — один автоматический повтор через 2–3 с, пока владелец «в сети» (`reachable`).
  
  Красный тест: фейковый ресивер шлёт `currentTime: 95`, затем обрыв → LOAD после переподключения содержит `currentTime ≈ 95`.
- **Объём:** 0,5–1 день.

### V7. У видео нет приоритета над массовой загрузкой: «Загрузить вообще всё» и T1 при входе участника

- **Критерий:** отзывчивость. **Важность:** средняя. Гипотеза о величине эффекта.
- **Сценарий:** во время видео пользователь жмёт «Загрузить вообще всё» (кнопка всегда на пульте, `Remote.tsx:163`; её же предлагает подсказка о медленном участнике, `Remote.tsx:129–133`). Хост тянет до 5 T2 одновременно с каждого источника, включая владельца видео. Владелец рендерит без перерыва (`turns`, `blobs.go:192–228`) и отдаёт ~3–10 T2/с × ~300 КБ ≈ 10–25 Мбит/с — того же порядка, что битрейт 4K. На хост сходятся потоки всех владельцев, и он же отдаёт видео на ТВ: эфир хоста делится, TCP справедлив по потокам, и 1 поток видео против 5–15 потоков T2 получает малую долю. То же, но короче, — при входе нового участника (фоновые T1, `blobs.go:533`, 5 работников на каждом узле).
- **Где:** `core/show/loader.go` (`plan`, `fetch`), `core/prefetch` (лимит 5 на источник, общий для окна и закреплений, A43). Нигде не учитывается, что сейчас играет видео.

### V9. Пока висит LOAD видео, «Следующий» не доходит до ТВ (до 20–30 с)

- **Критерий:** отзывчивость. **Важность:** низкая–средняя: случается, когда владелец «в сети», но отвечает медленно или не отвечает.
- **Сценарий:** на экране видео телефона, который только что заснул. Пульт жмёт «Следующий», курсор сдвигается, а ТВ ещё до ~20 с крутит загрузку видео.
- **Где:** `core/show/renderer.go:439–441, 489–492`: `drive` синхронно ждёт ответа на LOAD (`requestTimeout` 30 с). Ответ ресивера на LOAD приходит после загрузки медиа или ошибки, то есть после 502 хоста: dial 5 с или ожидание заголовков 20 с (`blobs.go:386`). Новый курсор обрабатывается только после этого. Склейка next/prev (A24) работает, но первый LOAD не прерывается.
- **Уверенность:** подтверждено чтением кода. Тестом на текущем фейковом ресивере не воспроизвести: он сам обрабатывает сообщения последовательно (`show/receiver_test.go:94–120`).
- **Класс:** баг в логике. Красный тест: ресивер, отвечающий на LOAD видео через 10 с и асинхронно принимающий следующие сообщения; после `Next()` LOAD следующего файла приходит меньше чем через 1 с. Правка: не ждать ответа LOAD в цикле `drive`, ответ сопоставлять по `requestId` (CAF прерывает прежний LOAD новым, `INTERRUPTED`).
- **Объём:** 0,5–1 день.

### V10. Конец видео: на ТВ заставка ресивера, «Воспроизвести», вероятно, даёт «Экран не выполнил команду»

- **Критерий:** понятность. **Важность:** низкая–средняя.
- **Сценарий:** видео доиграло. DMR переходит в IDLE/FINISHED и, по опыту, показывает свою заставку. На пульте «Воспроизвести». Нажатие шлёт PLAY со старым `mediaSessionId` (`cast.go:168–170`). Настоящий CAF после FINISHED, скорее всего, отвечает `INVALID_REQUEST`, и пульт показывает «Экран не выполнил команду. Попробуйте ещё раз.» — повтор тоже не поможет. Фейковый ресивер сессию после FINISHED не инвалидирует (`receiver_test.go:129`), поэтому тесты этого не ловят.
- **Где:** `core/show/renderer.go:504–513` (FINISHED не обрабатывается), `session.go:166–191`.
- **Уверенность:** гипотеза, проверить на ТВ.
- **Класс:** баг в логике: play при `player == IDLE` — это повторный LOAD (с `currentTime: 0`), а по FINISHED показать постер. Тест: фейк инвалидирует сессию по FINISHED → play даёт LOAD, а не `command_failed`.
- **Объём:** 0,5 дня.

### V11. Видео iPhone (.MOV) отправляется на Cast с `contentType: video/quicktime`

### V12. Нативный `readOriginal` на каждый МиБ заново открывает файл и делает лишнюю копию

- **Критерий:** ресурсы владельца (на плавность видео не влияет). **Важность:** низкая.
- **Где:** `app/modules/core/android/.../Renditions.kt:33–43`: на каждый вызов `openFileDescriptor` (binder к MediaProvider, без `ACCESS_MEDIA_LOCATION` — FUSE-редакция геоданных), новый `ByteBuffer` на 1 МиБ, `copyOf` даже при полном буфере. gomobile добавляет ещё 2–3 копии (`seq_android.c.support:209–219`, `seq_android.go.support:92`). `originalSize` — ещё одно открытие на каждый HTTP-запрос. В Go `original.Read` (`blobs.go:442–460`) читает целый МиБ даже для `Range: bytes=0-1` (замер: 1024 КиБ на 2 байта).
- **Оценка:** ~4 вызова в секунду на 4K30. Замер с имитацией 5 мс на вызов — всё равно ~1 Гбит/с. JVM получает ~2 МиБ мусора на МиБ потока (~10–20 МиБ/с на 4K): лёгкая нагрузка на GC владельца, возможны редкие подтормаживания его UI, но не видео.
- **Уверенность:** замер Go-части воспроизведён; нативная часть — подтверждено чтением кода.
- **Класс:** простая правка, по желанию: `buf.array()` без `copyOf` при полном чтении; кешировать открытый fd на последний `localID` с закрытием по простою; в Go ограничить кусок оставшейся длиной Range. Не срочно.
- **Объём:** 0,25 дня.

## Вход для TASK-43: требования к `OriginalSize`/`ReadOriginal` на iPhone

Интерфейс (`core/mobile/mobile.go:27–31`) менять не обязательно: он без состояния, и это удобно. Но нативная реализация должна выполнять следующее, иначе видео с iPhone будет тормозить или зависать сильнее, чем с Android.

1. **Произвольный доступ, а не последовательный.** `PHAssetResourceManager.requestData` отдаёт ресурс только с начала. Seek к `moov` в конце файла (типично для первого Range плеера) прочитал бы весь файл, а на каждый МиБ пришлось бы начинать заново. Нужен файл с `pread`/`FileHandle.seek`: `PHImageManager.requestAVAsset(forVideo:options:)` → `AVURLAsset.url` (локальный файл медиатеки), версия задаётся явно. Если вернулся `AVComposition` (slow-mo) или URL нет — запросить `.original` или (запасной путь) выгрузить `PHAssetResource` во временный файл через `writeData` и читать оттуда, с удалением по простою.
2. **Не открывать заново на каждый кусок.** `ReadOriginal` вызывается каждые 1 МиБ, на 4K это 5–10 раз в секунду, иногда параллельно (ТВ шлёт несколько Range). Асинхронный запрос PhotoKit на каждый кусок недопустим. Нужен кеш открытых дескрипторов: 1–2 последних `localID`, закрытие через ~60 с простоя и по memory warning. Реализация потокобезопасна.
3. **Бюджет времени.** `OriginalSize` и первый кусок должны укладываться в секунды: хост ждёт заголовки 20 с, а простой чтения — 10 с (A41). Каждый последующий `ReadOriginal` на 1 МиБ — десятки миллисекунд. Вызовы приходят из потоков Go: не ждать main queue, обработчики завершения PhotoKit — на фоновой очереди, иначе возможна взаимоблокировка с UI.
4. **Согласованность.** `OriginalSize` возвращает точную длину того же файла и той же версии (`.current` или `.original`), которые читает `ReadOriginal`. Это должна быть та же версия, что описана в AssetMeta (MIME, размер, ревизия). Отредактированное видео в `.current` — другой файл другой длины.
5. **iCloud — быстрая понятная ошибка, а не ожидание.** `isNetworkAccessAllowed = false`. Если оригинала нет на устройстве, ошибка за < 1 с с договорённым признаком. Ошибки gomobile из Swift доходят до Go только текстом, поэтому нужен префикс, например `not_local:`, а ядро сопоставляет его со своим `ErrNotLocal`. Ядро должно донести причину до пульта (V3). Неявно качать из iCloud нельзя: это минуты, возможно по сотовой сети.
6. **Ограничение памяти.** Не больше запрошенной длины (≤ 1 МиБ) на вызов, без загрузки файла в память (AC #4).
7. **Метаданные для понятных ошибок (TASK-43 AC #1):** заполнять `Codec` (`hvc1`/`avc1` из `CMFormatDescription` видеодорожки) и по возможности признак HDR/Dolby Vision. По ним хост сможет написать «видео в HEVC HDR» вместо общей ошибки (V2, §2.3). MIME — реальный (`video/quicktime` для .MOV); замену для Cast делает хост (V11).
8. **Фон (на стыке с TASK-44):** если приложение уходит в фон во время раздачи оригинала — `beginBackgroundTask`. По истечении корректно закрыть сокеты ядра, чтобы хост получил обрыв сразу, а не через 10 с простоя и 5 с dial (V5). Для будущего AirPlay-хоста: URL для `AVPlayer` external playback — LAN-адрес show-порта с токеном в пути. Заголовки (`AVURLAssetHTTPHeaderFieldsKey`) Apple TV при передаче URL не получит, а 127.0.0.1 ему недоступен.

## Что сделано хорошо и менять не нужно

- **Сквозной Range без хранения:** `ServeContent` поверх `io.ReadSeeker` из кусков (`blobs.go:423–471`). Range, 206, `Content-Range`, 416 и `If-Range` по ETag ревизии работают одинаково у владельца и через relay (тест `TestOriginalIsStreamedFromOwnerWithRanges` и замер). Память владельца ограничена одним куском.
- **Backpressure честный:** `io.Copy` без промежуточных буферов, и idle-таймаут A41 считается только пока хост ждёт владельца. Замер: пауза читателя в 3× таймаута не рвёт поток.
- **Брошенные запросы отменяются:** контекст запроса ТВ отменяет запрос к владельцу. После 20 оборванных Range горутины вернулись к исходному уровню. Перечитывание у владельца при обрыве ограничено буферами TCP.
- Go-путь (TLS 1.3, HTTP/1.1, общий транспорт с 8 простаивающими соединениями, A42) даёт на порядок больше, чем нужно 4K. HTTP/2 или свой транспорт не нужны (согласуется с §6 прошлого ревью).
- Show-порт для ТВ без `WriteTimeout` — правильно для длинного видео. LOAD на каждый слайд, склейка next/prev и `videoDown` с постером и подсказкой при 502 — хорошая основа. Её нужно лишь распространить на ошибки кодека и чтения (V2, V3).
- Собственное видео хоста идёт без relay — это лучший случай по эфиру. Стоит подсказывать его в V1/V4.
