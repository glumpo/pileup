## Согласованные пункты

### R01 — P2. Секрет pile раскрывается при обычном открытии экрана

**Требование:** §7.2 архитектуры и TASK-6, AC2: QR показывается только по кнопке; это пароль доступа к pile.

**Код:** [PileScreen.tsx](../app/src/screens/PileScreen.tsx), строки 32–49 и 81–88. `load()` при монтировании вызывает `api.invite`, затем без дополнительного действия выводятся QR и полная строка приглашения с секретом. Кнопка «Отправить приглашение» появляется уже после раскрытия.

**Сценарий:** пользователь открывает pile, чтобы перейти в хронологию или настроить загрузку; присутствующий рядом человек/камера получает бессрочный секрет. Отзыва/ротации секрета в текущем этапе нет по согласованной архитектуре, что повышает цену случайного раскрытия.

**Что требуется:** отдельное явное действие для раскрытия, начальное скрытое состояние, определённое поведение при уходе с экрана. [piles.test.tsx](../app/test/piles.test.tsx), строки 9–33, сейчас ожидает автоматическое получение/отображение приглашения: это пример тестирования реализации вопреки спецификации.

### R02 — P1. Нет согласованного жизненного цикла blob: ссылки, загрузка и очистка

**Объединение пунктов:** исходный R03 «Вытеснение разрушает другие ссылки на общий blob и чужие pins» включён в R02. Его причины, последствия и проверки учитываются в общей переработке жизненного цикла; отдельное исправление R03 не выделяется.

**Проблема проектирования:** состояние объекта распределено между планировщиком, загрузчиком, Node и файловым хранилищем. Нет общего владельца, который согласует удерживающие ссылки, выполняющуюся загрузку, публикацию результата и удаление.

В [node/blobs.go](../core/node/blobs.go), строки 85–110, проверка текущего asset выполняется до загрузки, а `SetRef` — после её завершения, без повторной проверки актуальности операции. В [show/loader.go](../core/show/loader.go), строки 277–302, загрузка использует общий контекст host, отдельной отмены объекта нет. [blob/blob.go](../core/blob/blob.go) самостоятельно переносит загруженный временный файл в постоянное хранилище, а refs записываются отдельно. Поэтому удаление может проиграть гонку завершению загрузки: уже ненужный объект появится снова.

Кроме того, `Evict` требует существующий asset с текущей revision, поэтому не может удалить уже исключённый файл или старую версию. Обычный HTTP-запрос удалённого asset отклоняется, но старые T1/T2 остаются на диске. Смена revision также оставляет неучтённые копии.

Есть и обратная ошибка: для существующего объекта `Evict` удаляет физический файл по хешу без проверки других ссылок ([node/blobs.go](../core/node/blobs.go), строки 154–163). Хранилище общее для Node, ref не содержит pile ID, а содержимое дедуплицируется по хешу. Поэтому вытеснение в одном pile может уничтожить копию, закреплённую в другом; разные asset с одинаковыми байтами могут потерять общее содержимое; совпадающие T1 и T2 маленького изображения могут лишиться миниатюры при вытеснении T2.

Другой загрузчик при этом способен продолжать считать объект загруженным: [show/loader.go](../core/show/loader.go), строки 90–94, проверяет наличие файла лишь однажды для ключа. Это следствие ошибочного удаления всё ещё удерживаемого содержимого. Исправление должно обеспечиваться storage и корректным учётом ссылок: действующая удерживающая ссылка не позволяет удалить объект. Отдельная синхронизация состояний загрузчиков между собой не требуется.

**Направление исправления:** общий для Node механизм управления жизненным циклом локальных объектов на уровне storage, со счётчиком удерживающих ссылок и единой процедурой очистки при переходе счётчика к нулю. Потребители получают и освобождают свои ссылки, прогрев сообщает необходимые файлы и их приоритеты. Кэш владеет бюджетом и политикой вытеснения (см. R04), а storage управляет состоянием объекта, выполняющейся попыткой и очисткой. Загрузчики не согласуют между собой собственные состояния.

Нужно различать два вида ссылок:

- Ссылки потребителей на логический объект `(owner, asset_id, revision, tier)`. Пока они существуют, объект нужен: ожидается загрузка либо удерживается готовая копия. Один запрос не должен отменять общую загрузку, если объект нужен другому потребителю.
- Ссылки логических объектов на физический файл по content hash. Разные asset/revision/tier могут иметь одинаковые байты; физический файл удаляется только после исчезновения последней удерживающей ссылки на него. До завершения загрузки content hash ещё неизвестен.

Считать следует причины удержания **локальной копии**, а не любое присутствие asset в хронологии: иначе T2 никогда не будет вытесняться. Обычное хранение в пределах бюджета тоже является причиной удержания; выход из окна не обязан немедленно удалять уже закэшированный объект. Удаление asset снимает удержание от соответствующего pile независимо от бюджета и pins этого pile. Действующие ссылки другого pile учитываются отдельно.

#### R02.1. Карта состояний и владение ссылками

Нужна общая для Node карта `ключ объекта → состояние объекта`. Ключ включает `(owner, asset_id, revision, tier)`, а не только asset ID: разные версии и T1/T2 должны различаться. Все пути загрузки/генерации этих объектов используют один механизм управления состоянием.

Запись содержит удерживающие ссылки и текущую фазу; для выполняющейся попытки — её идентичность, `cancel`, канал `done` и результат/ошибку; для сохранённого объекта — content hash. Нужен также способ уведомить ожидающих об окончании очистки. Это не обязательно публичный API с такими именами; обязательны описанные ниже свойства.

| Состояние | Поведение нового запроса на тот же ключ |
|---|---|
| Записи нет | После проверки актуальности asset и разрешённости доступа создаётся запись и одна попытка загрузки. |
| `loading` | Запрос присоединяется к существующей попытке, добавляя собственную удерживающую ссылку. Вторая загрузка не запускается. |
| `ready` | Запрос получает существующий объект с собственной ссылкой. Контекст завершённой загрузки уже должен быть освобождён после её финализации. |
| `failed` | Ошибка попытки известна; повтор выполняется по принятой политике ошибок только после завершения предыдущей попытки. Одновременные повторы объединяются в одну новую попытку. |
| `cleaning` | Новая загрузка заблокирована. Запрос ждёт окончания очистки с возможностью отменить своё ожидание. К отменяемой старой попытке он не присоединяется. |
| `cleanup_failed` | Очистка не завершилась успешно; ошибка сохранена. Новую загрузку нельзя начинать поверх неразобранного старого состояния. Предусмотрен повтор очистки; ожидающие получают ошибку, а не зависают навсегда. |

Основной путь: `нет записи → loading → ready → cleaning → нет записи`. Удаление во время работы даёт `loading → cleaning → нет записи`. После ошибки очистки запись остаётся, чтобы следующий вызов мог повторить уборку; состояние не теряется вместе с ошибкой.

Подписки, снятие ссылок и переходы состояния синхронизируются. При снятии последней ссылки запись переводится в `cleaning` **до освобождения блокировки** и остаётся в карте до окончания очистки. Поэтому новый запрос видит очистку и не может начать конкурирующую попытку. После ожидания он заново проверяет состояние и актуальность asset/revision: за это время файл мог быть исключён из pile.

Освобождение относится к конкретному выданному удержанию. Повторный вызов для одного удержания идемпотентен и не уменьшает счётчик второй раз; освобождение двух разных удержаний корректно уменьшает его дважды. Старое удержание/завершение не может изменять запись новой попытки с таким же ключом. Счётчик не бывает отрицательным.

#### R02.2. Канал завершения попытки и процедура очистки

Канал `done` принадлежит **конкретной попытке**, а не всем будущим загрузкам файла. Его закрывает ровно один владелец — код завершения этой попытки. Функция очистки вызывает `cancel` и ждёт канал, но сама его не закрывает.

Закрытие `done` означает: попытка больше не выполняет и не выполнит запись, её результат/ошибка зафиксированы, файловые дескрипторы/HTTP body закрыты, освобождение временных ресурсов выполнено либо его ошибка записана. Это включает загрузку, обработку и сохранение, а не только получение последнего сетевого байта. При успехе постоянный файл может оставаться в storage: его удерживают ссылки.

Если удалить временный файл не удалось, `done` всё равно закрывается после окончания работы и фиксации ошибки. Иначе ожидание превращается в вечное зависание. Ошибка освобождения ресурсов доступна процедуре очистки, которая должна обработать её и повторить уборку, когда это возможно.

Порядок удаления:

1. Под блокировкой снять последнюю ссылку, перевести запись в `cleaning` и запретить публикацию результата старой попытки. Извлечь её `cancel`/`done`. Владелец очистки для этой записи должен быть один.
2. Освободить блокировку, вызвать `cancel` и дождаться `done`. Отмена является сигналом, а не ожиданием. Нельзя ждать под мьютексом, который нужен завершающейся попытке.
3. После `done` проверить storage и убрать остатки временных данных, ref и больше не удерживаемое содержимое. Очистка обязательна и при уже завершившейся успешной загрузке: ждать в этом случае не придётся, канал уже закрыт.
4. Удаление ссылки логического объекта и решение об удалении физического content hash согласовать с другими логическими объектами. Проверка числа ссылок и удаление не должны гоняться с публикацией новой ссылки на тот же hash. Блокировки только по логическому ключу для этого недостаточно.
5. После успешной очистки удалить из карты именно очищаемую запись и уведомить ожидающих. При ошибке сохранить `cleanup_failed` и сообщить ошибку. Повторное удаление во время очистки присоединяется к её результату; после успеха становится безопасным no-op, после ошибки позволяет повторить уборку.

**Завершение попытки и завершение очистки — разные события.** Закрытый `done` разрешает проверку/уборку storage, но ещё не разрешает новую загрузку. Новый запрос ждёт уведомления об окончании `cleaning`, например отдельного канала очистки или уведомления об изменении состояния. При пробуждении состояние проверяется заново.

Публикация результата должна быть согласована с переходом в `cleaning`: если удаление выиграло гонку, завершение не переводит запись обратно в `ready` и не создаёт действующий ref. Одного `ctx.Err()` перед независимым `Put` недостаточно. Если какие-то байты уже сохранены до отмены, процедура очистки после `done` гарантированно обнаруживает их и обрабатывает. Для новой попытки создаются новые контекст и канал.

После удаления/смены revision очистка использует сохранённый ключ и сведения о содержимом, а не требует найти прежнюю версию в текущей проекции. Сеть, обработка и ожидание каналов не выполняются под общим мьютексом карты; очистка одного ключа не должна останавливать работу остальных файлов.

#### R02.3. Контексты, ошибки и остановка

У каждой реально запущенной попытки есть отдельный контекст и явный владелец `CancelFunc`. Он вызывает `cancel` при любом завершении, включая успех и ошибку, обычно через `defer cancel()`. Путь удаления может вызвать тот же cancel раньше. Порядок финализации гарантирует, что к закрытию `done` контекст и прочие ресурсы попытки уже освобождены либо ошибка освобождения зафиксирована. Успешное завершение освобождает контекст операции, но не ссылку, удерживающую готовый файл в кэше.

Контекст общей загрузки не должен принадлежать первому случайному UI-запросу. Отмена одного потребителя снимает только его участие; пока есть другие ссылки, общая работа продолжается. Отмена запроса, ожидающего очистку, прекращает только его ожидание: обязательная очистка продолжается. Она не должна использовать уже отменённый контекст загрузки как условие, позволяющее пропустить уборку.

Ожидаемая отмена из-за отсутствия потребителей не считается поломкой файла или недоступностью source. При остановке Node новые попытки запрещаются, действующие отменяются, ожидающие получают завершение/ошибку, а работающие операции и их финализация учитываются до закрытия общих ресурсов.

Текущий нативный `RenditionMaker.Rendition` не принимает контекст/сигнал отмены. Пока провайдер не умеет прерывать обработку, `done` закрывается после её фактического возврата и финализации. Поздний отменённый результат отбрасывается и не публикуется. Закрывать канал раньше, чтобы имитировать немедленную отмену, нельзя.

После рестарта удержание сохранённых объектов восстанавливается из постоянных ссылок/состояния кэша и pins; один счётчик в памяти недостаточен. Временные файлы и незавершённые изменения storage требуют согласования при открытии. Контексты и каналы старого процесса не восстанавливаются.

#### R02.4. Обязательные тестовые сценарии

Двух базовых тестов «удаление в процессе» и «удаление после успеха» недостаточно для этой асинхронной логики. Нужны разные порядки событий, повторные вызовы, ошибки и конкурирующие потребители. Ниже — сценарии будущих тестов; реализация и запуск тестов в рамках обсуждения не выполняются.

| № | Сценарий | Проверяемый результат |
|---|---|---|
| 1 | Удаление во время сетевой загрузки | Последняя ссылка вызывает отмену; работа завершается, `done` закрывается после финализации; после окончания очистки нет временного файла, постоянного объекта без других ссылок и ref. |
| 2 | Удаление во время локальной обработки, которая не поддерживает отмену | Очистка ждёт реального возврата провайдера. До него `done` открыт и новая попытка заблокирована. Поздний результат отбрасывается, после финализации очистка завершается. |
| 3 | Удаление во время сохранения | Отдельные контролируемые остановки на записи временного файла, перед/после публикации постоянного файла и перед/после записи ref. Для обоих порядков «завершение раньше удаления» и «удаление раньше завершения» итог одинаков: удалённый объект не появляется снова. |
| 4 | Удаление после успешной загрузки | Пока есть ссылка, готовый файл доступен; контекст попытки уже освобождён. После последнего освобождения ref и неиспользуемый файл удалены; ждать завершённую попытку повторно не приходится. |
| 5 | Два удаления/освобождения подряд | Повторное освобождение одного удержания не уменьшает счётчик повторно. Второе удаление уже очищенного объекта безопасно. Отдельно проверить, что освобождение двух разных удержаний учитывается дважды. |
| 6 | Два удаления одновременно | Очистка запускается один раз, вызовы получают согласованный результат. Нет отрицательного счётчика, повторного закрытия канала, двойной финализации или зависания. Проверить также общий результат ошибки очистки. |
| 7 | Загрузка → удаление → новая загрузка того же ключа | Новый запрос приходит до закрытия старого `done` либо после `done`, но до окончания очистки. В обоих вариантах новая попытка начинается только после очистки. Несколько новых запросов объединяются в одну попытку; старое освобождение не затрагивает её результат. Проверить также путь через уже готовый файл. |
| 8 | Отмена запроса, ожидающего очистку | Ожидание завершается по контексту запроса; лишняя ссылка и загрузка не возникают. Сама очистка завершается независимо от этого запроса. |
| 9 | Несколько потребителей одного ключа; один отменяется | Выполняется одна загрузка. Отмена одного потребителя не отменяет работу и не удаляет данные, нужные остальным; результат доступен оставшимся. |
| 10 | Все потребители освобождают ссылки в разных порядках | Ровно переход к нулю инициирует отмену/очистку. Запоздалые callback и повторные освобождения не влияют на следующую запись того же ключа. |
| 11 | Новое удержание одновременно со снятием последней старой ссылки | Если новое удержание зарегистрировано раньше перехода к нулю, объект остаётся нужен и не удаляется. Если раньше началась очистка, новый запрос ждёт и затем проходит обычное получение заново. Нет промежуточного состояния «новая ссылка есть, а её объект удалён». |
| 12 | Разные логические объекты/два pile/T1 и T2 с одинаковым content hash | Удаление одной ссылки не уничтожает файл, пока другой объект его удерживает, в том числе через pin. Последняя ссылка удаляет содержимое. Учитывается фактическая доступность файла, а не только значение счётчика. |
| 13 | Публикация нового объекта с тем же hash одновременно с физическим удалением | Новый действующий ref никогда не указывает на удалённый файл. Проверяются оба порядка регистрации новой ссылки и удаления последней старой. |
| 14 | AssetRemove или смена revision, пока запрос ждёт очистку | После ожидания доступ и актуальность проверяются заново. Запрос из pile, где asset удалён, не запускает его заново. Очистка старой revision не затрагивает новую; действующие ссылки другого pile сохраняются. |
| 15 | Ошибка загрузки, обработки, записи или сохранения ref; затем повтор | На каждом пути контекст освобождён, `done` закрыт, ресурсы завершены либо ошибка их уборки передана дальше. Повтор не наследует отменённый контекст/закрытый канал и не пересекается с прежней попыткой. |
| 16 | Ошибка удаления временного файла, ref или постоянного файла; затем повтор очистки | Запись не исчезает как будто уборка успешна. Ожидающие получают ошибку; новая загрузка не запускается поверх `cleanup_failed`. После устранения причины повтор завершает уборку, включая уже частично удалённые данные. |
| 17 | Успешное завершение при остающихся ссылках | Контекст попытки отменён и связанные ресурсы освобождены, хотя файл продолжает храниться. Повторить проверку для ошибки и ранней отмены. Этот тест отдельно ловит утечки успешных операций, которые тесты удаления не выявляют. |
| 18 | Остановка Node во время загрузки, очистки и ожидания нового запроса | Новая работа не стартует, ожидающие разблокируются с определённым результатом, операции отменяются и завершаются без зависших горутин. Для неотменяемого нативного fake дождаться его контролируемого возврата: немедленная остановка такого провайдера не обещается. |
| 19 | Рестарт после незавершённой записи/частичной очистки | Временные остатки и осиротевшие объекты обработаны; ссылки восстановлены согласованно. Содержимое с действующим pin/ссылкой другого pile не потеряно, старые счётчики в памяти не считаются источником истины. |
| 20 | Работа другого ключа, пока первый загружается или очищается | Ожидание медленного source/провайдера/`done` одного объекта не удерживает общий мьютекс и не блокирует независимую загрузку или чтение другого объекта. |

**Сценарий 12 раскрыть отдельными тестами из исходного R03:**

- **Один файл в двух pile:** загрузить T2, закрепить его в pile A, затем вытеснить из pile B. Отключить источник и проверить, что файл по-прежнему читается через pile A благодаря оставшемуся удержанию. Освобождение ссылки B не должно удалять общую ref или содержимое, пока они нужны A.
- **Два разных asset с одинаковым содержимым:** подтвердить разные логические ключи и один content hash. Вытеснить первый объект; второй должен оставаться доступным без повторной загрузки. Затем снять все оставшиеся удержания и проверить удаление физического файла. Объект удерживается не только pin: снятие pin само по себе не требует удаления, если остаётся обычное удержание кэшем или другим потребителем.
- **Одинаковые байты T1 и T2:** сохранить оба представления маленького изображения с общим hash. После вытеснения T2 запрос T1 продолжает читать существующую миниатюру при недоступном источнике. Очистка T2 не снимает ссылку T1; после снятия всех удержаний содержимое удаляется.

В этих тестах проверять storage и учёт ссылок: готовый файл читается без повторного сетевого получения, пока остаётся хотя бы одно удержание; освобождение одной ссылки не снимает чужие; после освобождения последней ссылки и завершения очистки ref и физический файл отсутствуют. Проверка взаимной синхронизации загрузчиков не нужна: корректность обеспечивается единым контрактом storage.

Синхронизацию тестов задавать управляемыми каналами/барьерами на границах загрузки, сохранения, публикации и очистки. Произвольный `sleep` не доказывает, что нужная гонка проверена. Для каждого граничного события проверять оба значимых порядка; после завершения проверять и доступность/отсутствие данных в storage, и завершение запросов/контекстов, и число реально начатых операций. Тесты не должны ограничиваться проверкой имён внутренних состояний.

Помимо детерминированных сценариев нужны повторяемые серии операций acquire/release/load/delete с разными расписаниями и прогон с Go race detector при реализации. Race detector ловит несинхронизированный доступ к памяти, но сам по себе не выявляет логическую гонку «старое удаление уничтожило новый результат» — для неё нужны перечисленные проверки результата. Количество живых горутин в процессе само по себе ненадёжный критерий; завершение конкретных операций проверяется через их сигналы и управляемые провайдеры.

Это требования к последующей переработке, а не описание внесённых исправлений. В рамках обсуждения изменён только этот документ; код и тесты не менялись и не запускались.

### R04 — P1. Бюджет и учёт содержимого кэша ошибочно возложены на вызывающий код

**Принцип:** бюджет — часть кэша. Любой полученный через него объект должен автоматически попадать в учёт и подчиняться общей политике хранения. Корректность этого учёта не должна зависеть от того, кто запросил файл: viewer, Cast, прогрев или ручная загрузка, и запущен ли вообще показ.

**Существующая ошибка:** дисковый кэш используется, но его бюджет учитывается только на отдельных путях вызова.

- [Viewer.tsx](../app/src/screens/Viewer.tsx), строки 26–35, запрашивает T2 через HTTP API. [httpapi/blobs.go](../core/httpapi/blobs.go), строка 27, вызывает `Node.Blob`, который проверяет storage и при необходимости получает, сохраняет и возвращает объект ([node/blobs.go](../core/node/blobs.go), строки 85–110).
- Загрузчик показа вызывает тот же `Node.Blob`, но затем отдельно узнаёт размер файла и вызывает `l.cache.Loaded(k, size)` ([show/loader.go](../core/show/loader.go), строки 277–302). Только этот дополнительный вызов сообщает планировщику о поступивших байтах.
- HTTP-обработчик такого вызова не делает. Первоначальный обход `Cached` в `loader.setItems` (строки 90–94) не решает проблему: наличие файла проверяется один раз для ключа, и позднее появившийся T2 может остаться неучтённым.

**Пример:** при первом обходе T2 фотографии отсутствовал, а загрузчик уже пометил её ключ как проверенный. Пользователь открыл фотографию в viewer; ядро получило и сохранило, например, 5 МиБ T2. Storage вырос на 5 МиБ, но учёт бюджета планировщика не изменился. При следующем обходе этот ключ пропускается как уже проверенный. Долгое листание таким способом накапливает T2 вне штатного учёта и вытеснения. Если показ вообще не запускался, корректный бюджет всё равно должен работать.

**Предлагаемое устройство:**

1. **Единый вход получения кешируемого объекта.** Viewer, Cast, прогрев и ручная загрузка используют один контракт кэша: получить объект/удерживающую ссылку и освободить её после использования. `Node.Blob` может остаться фасадом проверки доступа и актуальности asset, но получение T1/T2 внутри него должно проходить через этот контракт.
2. **Публикация и учёт принадлежат кэшу.** Кэш сам организует загрузку или генерацию, сохранение и регистрацию размера/ссылки. Вызывающий код не обязан отдельно делать `Stat`, вызывать `Loaded` или уведомлять о появлении файла. Не должно существовать публичного пути «сохранить кешируемый blob, но забыть учесть его». Низкоуровневые операции записи остаются внутренней частью общего механизма.
3. **Бюджет и вытеснение находятся внутри кэша.** Кэш знает учитываемые объекты, их размеры, `taken_at` и причины защиты. При изменении содержимого или удержаний он сам применяет принятую политику: в первую очередь вытесняет незащищённые объекты с самым ранним `taken_at`, сохраняя текущий файл, окно и pins. Чистый алгоритм выбора жертв можно сохранить как внутренний компонент кэша; протаскивать его учёт в каждый вызывающий модуль не нужно.
4. **Прогрев задаёт спрос.** Курсор и окно определяют, какие файлы потребуются и с каким приоритетом. Потребители сообщают эту потребность и закрепления через контракт кэша. Поддержание бюджета уже загруженных файлов работает независимо от наличия активного прогрева или внешнего экрана.
5. **Вытеснение использует жизненный цикл R02.** Кэш освобождает своё удержание, а storage при исчезновении последней ссылки выполняет отмену/ожидание/очистку. Действующий читатель, другой pile или pin может продолжать удерживать содержимое. Общий физический файл нельзя удалять только потому, что один потребитель больше в нём не нуждается.

Запрос пользователя и обычное удержание кэшем имеют разное время жизни. Завершение HTTP-ответа освобождает ссылку читателя, но не обязано сразу удалять файл: кэш может сохранить собственное удержание для повторного просмотра. Решение о снятии такого удержания принимает сам кэш по своему бюджету. Это позволяет совместить повторное использование данных с очисткой по нулю ссылок из R02.

Существующую область бюджета, например бюджет на pile из A26, можно сохранить при этой переработке: в неё должны попадать все соответствующие загрузки независимо от их инициатора. Общие физические байты по content hash и отнесение содержимого к бюджетам pile необходимо учитывать последовательно; ни повторный запрос одного объекта, ни дедупликация не должны приводить к случайному удвоению или пропуску учёта. Изменение области бюджета — отдельное решение, не следствие переноса ответственности внутрь кэша.

Бюджет остаётся мягким в оговорённых архитектурой случаях: защищённые окно/pins могут превышать его. Это превышение должно быть явно учтено. Сохранённые байты не должны исчезать из учёта только потому, что их получил другой модуль или попытка очистки завершилась ошибкой; физический и логический учёт должны отражать соответствующие им реальные объекты и ссылки.

**Проверки при реализации:**

- Получать T2 через настоящий HTTP-путь viewer без запуска Show. Все успешно сохранённые T2 учитываются, а при превышении бюджета старые незащищённые объекты вытесняются по принятой политике.
- Смешать запросы viewer, Cast, прогрева и ручной загрузки. Они используют один учёт; повторный/конкурентный запрос того же объекта не создаёт дополнительную копию и не увеличивает учтённый размер повторно в той же области бюджета.
- Проверить освобождение ссылки HTTP-читателя: файл может остаться в пределах бюджета; последующее вытеснение корректно освобождает удержание кэша и проходит процедуру R02. Пока другой потребитель держит ссылку, содержимое остаётся доступным.
- Проверить превышение бюджета при защищённых объектах и pins, затем снятие защиты. Защищённые данные сохраняются, фактическое превышение видно в учёте, а после снятия защиты применяется обычная политика вытеснения.
- Проверить ошибки получения, сохранения и очистки, повтор и рестарт: нет пропущенных/дважды учтённых объектов; состояние содержимого восстанавливается без обязательного запуска загрузчика показа. Сохранить проверки общих hash и разных pile из R02.

Передача курсора viewer для прогрева остаётся отдельной частью интеграции с требованиями §6.2. Размер окна телефонного viewer здесь не пересматривается. Корректный бюджет необходим и для одиночного запроса без какого-либо окна предзагрузки.

Сформулировано как требование к последующей переработке. Код и тесты в рамках обсуждения не менялись и не запускались.

### R05 — P2. Две очереди с приоритетом viewer и общий лимит загрузок на источник

**Существующая проблема:** фоновая загрузка T1, прогрев T2 разных pile и запросы viewer/renderer получают данные независимо. Локальный предел в одном планировщике не ограничивает их суммарную активность. В текущем коде `prefetch.PerSource = 5`, а `node.fetchers = 5` задаёт отдельное число работников T1. Общего ограничения на источник нет.

**Согласованное изменение:** для удалённых загрузок T1/T2 установить **7 одновременно выполняющихся запросов к одному owner на весь Node**, независимо от pile и инициатора. Для каждого owner предусмотреть два канала заявок: **обычный (`normal`) с буфером на 20 заявок** и **срочный (`urgent`) для запросов viewer**. При выборе следующей заявки сначала неблокирующе проверять urgent; если он пуст, выполнять `select` между urgent и normal. Это заменяет прежнее требование пяти загрузок и уточняет ранее выбранную единую FIFO-очередь; само architecture.md и Backlog в рамках обсуждения не редактируются.

#### R05.1. Структура и общие константы

Использовать общую для Node карту `owner → ограничитель источника`. Owner определяется ключом устройства, а не IP-адресом. Запись содержит:

- обычный канал заявок normal вместимостью 20;
- отдельный канал urgent для запросов viewer;
- один общий для обоих каналов семафор на 7 активных загрузок;
- управление выбором следующей заявки и завершением работы ограничителя.

Буфер семафора и каналы заявок выполняют разные функции. Канал токенов на 7 элементов ограничивает суммарный параллелизм, а normal/urgent содержат заявки соответствующего класса. Для каждого owner нужен один порядок диспетчеризации: запросы не должны обходить выбор между очередями и независимо состязаться за семафор. Порядок сохраняется внутри каждого класса, а срочные заявки получают преимущество перед обычными по алгоритму ниже.

Дополнительный буфер urgent для этого алгоритма не обязателен: допустим небуферизированный канал, где viewer ждёт приёма заявки или отмены своего ожидания. Ёмкость urgent отдельно не зафиксирована этим решением; автоматически создавать второй буфер на 20 и считать, что общий объём очередей остался прежним, нельзя. Согласованная общая константа 20 применяется к normal и размеру прогрева.

Карта создаёт ровно одну запись на owner даже при одновременных первых запросах. В качестве простого варианта записи могут жить до остановки Node: удалять «неактивную» запись и случайно создать второй независимый семафор для ещё используемого owner нельзя. Общий мьютекс карты нужен только для доступа к записям; ожидание очереди, семафора и сети выполняется без него.

Вынести общие значения в небольшой Go-пакет, например `core/limits` (отдельного пакета констант в текущем дереве не найдено):

- `PrefetchAhead = 20` — число следующих элементов прогрева и вместимость normal;
- `MaxDownloadsPerOwner = 7` — общий предел параллельных загрузок с источника.

Планировщик и ограничитель используют эти определения, без независимых копий чисел. Текущий элемент дополняет 20 следующих при построении окна, а 20 мест normal не включают 7 выполняющихся операций. Существующие ограничения нужно различать по смыслу: размер отдельного пула работников не автоматически равен лимиту на owner. Если где-то остаётся проверка именно общего лимита источника, она должна использовать согласованную константу 7.

#### R05.2. Порядок выполнения и отмена

Единая точка ограничения находится в общем пути фактического получения удалённых T1/T2. Сейчас все такие получения проходят через [Node.fetch](../core/node/blobs.go), строки 191–208; после переработки R02/R04 этот путь также должен оставаться общим. Попадание в готовый кэш не занимает сетевой слот. Несколько потребителей одного объекта, объединённые механизмом R02, используют одну фактическую попытку и один слот, даже если эта попытка получила срочный приоритет после постановки в normal.

Правила исполнения:

1. Направить запрос viewer в urgent, остальные заявки — в normal данного owner. Постановка/передача в оба канала отменяема. Полный normal задерживает его производителей, но не блокирует доступ к urgent. Буфер normal не расширяется и дополнительная внутренняя очередь не создаётся. Ограничение буфера не означает отсутствия вызывающих, ожидающих снаружи.
2. Сначала дождаться свободного общего слота, затем выбирать заявку. Нельзя заранее извлечь обычную заявку и ждать с ней занятого семафора: иначе она окажется перед срочными запросами, которые появились за время ожидания. Не резервировать несколько обычных заявок за пределами канала.
3. При доступном слоте сначала выполнить неблокирующее чтение urgent через `select` с `default`. Если срочная заявка доступна, взять её. Если нет — выполнить блокирующий `select` между urgent, normal и отменой контекста ограничителя. После получения проверить актуальность заявки и состояние остановки перед запуском. Если слот был зарезервирован, но операция не стартует из-за отмены/устаревшей заявки/остановки, вернуть его.
4. FIFO сохраняется внутри соответствующего канала. У одновременно поступающих вызовов нет заранее определённого общего порядка; завершение семи параллельных загрузок может происходить в любом порядке. Приоритет urgent действует на выбор следующей работы и не прерывает уже выполняющиеся обычные загрузки.
5. Отменённая заявка не начинает загрузку. Если её запись ещё находится в канале, при извлечении она пропускается. Отмена и начало исполнения согласованы с состоянием попытки из R02: после закрытия её `done` она уже не может быть запущена поздним обработчиком. Повторный выбор после пропуска устаревшей заявки снова учитывает приоритет urgent.
6. Активный слот удерживается до фактического завершения выполняющейся загрузки и финализации её ресурсов. Один вызов `cancel` не освобождает слот преждевременно. Освобождение выполняется ровно один раз при успехе, ошибке или отмене.
7. Заполненные очереди или зависший источник A не мешают независимому owner B получать свои слоты. При остановке Node новые заявки не принимаются, ожидающие в обоих каналах завершаются, активные попытки отменяются и финализируются по R02. Ожидание канала при уже зарезервированном слоте также должно прерываться остановкой без потери слота.

**Точная гарантия приоритета:** один `select` с двумя готовыми каналами не предпочитает urgent. Предварительная неблокирующая проверка обеспечивает выбор срочной заявки, которая уже доступна на этом шаге. Если urgent появился после проверки и оба канала стали готовы к следующему `select`, может быть выбран normal. Это допустимая граница предложенного алгоритма; абсолютный атомарный приоритет для одновременного поступления не обещается. При непрерывном потоке urgent обычные заявки могут ждать долго; квота гарантированного обслуживания normal в этом решении не вводится.

**Viewer присоединяется к уже ожидающему прогреву:** если объект уже стоит в normal, новый потребитель viewer должен повысить приоритет той же попытки, а не остаться ждать за фоном и не создать вторую загрузку. Допустимый способ — передать в urgent ссылку на ту же попытку, оставив в normal старую запись. Право запустить попытку захватывается атомарно; последующее извлечение второй записи её не запускает и не финализирует повторно. Если попытка уже выполняется или завершилась, viewer использует её результат; ожидание постановки в urgent не должно задерживать получение уже доступного результата. Несколько присоединившихся viewer не должны бесконтрольно размножать заявки повышения приоритета. Отмена одного viewer снимает только его удержание: другие потребители той же попытки учитываются по R02.

Устаревший прогрев отменяется через снятие соответствующих удержаний по R02. Это освобождает ненужную работу без нарушения живых ссылок других потребителей.

#### R05.3. Проверки при реализации

- **Общий лимит двух каналов:** одновременно запустить T1, прогрев нескольких pile и viewer/renderer к одному owner. Срочные и обычные загрузки суммарно не превышают 7; повторные потребители того же объекта не создают дополнительные сетевые операции.
- **FIFO внутри класса:** последовательно поставить различимые заявки одного класса, затем освобождать слоты по одному. Следующая начавшая работу живая заявка соответствует порядку этого класса. Порядок завершения параллельных работ не фиксировать.
- **Приоритет уже ожидающего viewer:** занять все 7 слотов обычными загрузками, поставить normal и обеспечить ожидающую urgent-заявку, затем освободить один слот. Следующей запускается urgent; обычная заявка не должна быть заранее извлечена и зарезервирована перед ней. После исчерпания urgent normal продолжает исполняться.
- **Пустой urgent:** обычная работа запускается без ожидания появления viewer. Если оба канала пусты, диспетчер ждёт поступления/остановки без активного опроса.
- **Граница предварительной проверки:** управляемо поставить urgent между неблокирующей проверкой и общим `select`. Тест допускает оба выбора и проверяет отсутствие потери заявки, нарушения общего лимита и повторного запуска; не требовать абсолютного приоритета, которого этот алгоритм не гарантирует.
- **Полный normal:** удерживать 7 активных операций и заполнить 20 мест normal. Следующий обычный вызов ждёт постановки с возможностью отмены, но urgent остаётся доступен своему производителю и выбирается первым при освобождении слота, если уже ожидает на предварительной проверке.
- **Отмена в обоих каналах:** отменить заявку в начале, середине и конце normal и отменить ожидающие urgent. Они не обращаются к источнику, оставшиеся сохраняют порядок своего класса, позднее извлечение отменённой заявки не воскрешает завершённую попытку.
- **Повышение приоритета общей попытки:** поставить объект в normal, затем запросить его из viewer. Он получает срочное обслуживание, но загружается ровно один раз. Позднее чтение старой записи normal не вызывает повторной загрузки, освобождения слота или закрытия `done`. Проверить также нескольких viewer, начало/завершение normal одновременно с повышением приоритета и отмену одного из потребителей при оставшихся удержаниях.
- **Отмена одновременно со стартом:** проверить оба порядка — отмена до получения права на исполнение и после старта. Нет двойного запуска, преждевременного освобождения слота, повторной финализации или работы после `done`.
- **Освобождение активного слота:** успех, HTTP-ошибка, ошибка сохранения и отмена освобождают слот ровно один раз после завершения операции. Пока отменяемый обработчик ещё выполняется, следующая заявка не должна доводить число активных операций выше 7.
- **Независимые источники и создание карты:** одновременные первые запросы одного owner используют один ограничитель. Полная очередь A не блокирует B; смена адреса того же устройства не создаёт второй лимит.
- **Остановка Node:** при заполненном normal, ожидающих urgent и занятых слотах завершаются ожидающие и активные операции, не остаются диспетчер или заявки, удерживаемые навсегда. Отдельно проверить ожидание пустых каналов после резервирования слота. Использовать управляемые барьеры и проверки конкретных операций, как в R02.

### R06 — P1. Неудачный LOAD считается успешным и не повторяется для текущего кадра

**Причина:** в [renderer.go](../core/show/renderer.go), строки 116–131, `loaded = url` выполняется до результата `s.cast.Load`. После ошибки тот же URL уже считается загруженным, поэтому следующий проход не вызывает для него LOAD. Кроме того, цикл затем ждёт события в `select` (строки 137–150): одно исправление присваивания не гарантирует повтор, поскольку появление T2 в storage само по себе этот цикл не будит. `status` (строки 168–174) сообщает о поздней ошибке Cast, но также не сбрасывает признак успешного LOAD.

#### R06.1. Сценарий воспроизведения

Сценарий выведен из кода; в рамках ревью не запускался.

1. На host есть метаданные фотографии другого участника, но её T2 ещё отсутствует в локальном storage. Cast-соединение с телевизором установлено.
2. Сделать source недоступным и перейти на эту фотографию. Host отправляет LOAD с её URL, а запрос изображения со стороны receiver завершается ошибкой. Cast возвращает ошибку LOAD либо позднее сообщает ошибку загрузки через MEDIA_STATUS.
3. Не менять текущий кадр и не перезапускать показ. Вернуть source в сеть и дождаться, пока T2 станет доступен host.
4. В текущей реализации URL остаётся в `loaded`; повторный LOAD этого кадра не отправляется. Восстановление storage и исчезновение Waiting не означают восстановления изображения на ТВ.

**Ожидаемый результат:** после восстановления источника host автоматически повторяет LOAD актуального кадра, receiver успешно получает фотографию, ошибка снимается, повторы прекращаются.

В [show_test.go](../core/show/show_test.go), строки 370–424, существующий тест проверяет появление файлов в кэше и исчезновение Waiting после возвращения source. Он не проверяет повторный LOAD текущего URL и получение содержимого receiver.

Если такой статус пришёл уже в ответе на LOAD, его также нельзя считать успехом только потому, что Go-вызов вернул `err == nil`.

#### R06.3. Предложенный локальный вариант исправления

### R07 — P3. При долгом ожидании видеопотока нужны таймауты, повтор и индикатор загрузки

**Оценка после обсуждения:** приоритет снижен с P1 до P3. Это онлайн-просмотр, поэтому проблема с воспроизведением сразу заметна пользователю. Основное требование к доработке — понятное состояние ожидания и повтор после таймаута.

**Существующая проблема:** оригинал видео передаётся через host потоком. [node.go](../core/node/node.go), строка 282, создаёт stream-клиент без общего Timeout; Transport также не задаёт ResponseHeaderTimeout. В [blobs.go](../core/node/blobs.go), строки 308–334, нет явного ограничения ожидания данных от источника, а ошибка `io.Copy` игнорируется. Поэтому запрос может надолго остаться в ожидании без управляемого перехода к повтору. Само отсутствие общего таймаута на весь длинный видеозапрос ошибкой не является.

**Сценарий:** открыть видео с другого телефона; источник принимает соединение, но не отвечает заголовками либо перестаёт отдавать данные после начала воспроизведения. Пользователь видит остановившийся просмотр, а host продолжает ждать. Возвращение источника должно позволить повторить получение без ручного перезапуска всей сессии.

**Предложенное поведение:**

1. Ограничить ожидание заголовков и ожидание чтения данных от source. Длинное исправное воспроизведение не должно обрываться из-за суммарной длительности запроса. Пауза пользователя или ожидание со стороны получателя сами по себе не означают таймаут источника.
2. После таймаута завершать неудавшуюся попытку и выполнять повтор с паузой. Повтор относится к актуальному видео; смена файла, остановка показа и отмена запроса прекращают ненужные повторы. Освобождение соединений, HTTP body, таймеров и контекстов требуется на всех путях.
3. При долгом ожидании показывать **крутящийся индикатор загрузки (spinner, прогресс без процентов)**. Он остаётся видимым во время ожидания/повторов и исчезает при возобновлении воспроизведения, смене файла либо остановке. UI получает явный признак ожидания; замерший кадр не должен выглядеть как успешно продолжающееся воспроизведение.
4. Для Cast индикатор в управляемом приложением UI можно показать на экране управления host. Отрисовка самого телевизора зависит от receiver; доработка его интерфейса не является условием этого пункта. В собственном viewer индикатор показывается непосредственно в области просмотра.
5. Обрабатывать и передавать в существующую логику показа ошибки чтения/копирования, а не терять их. Повтор после уже начатого HTTP-ответа должен использовать корректный новый запрос/действие renderer с учётом Range; нельзя дописывать начало файла заново в прежний частично отправленный ответ. Постоянную ошибку не следует скрывать бесконечным spinner.

**Недостающие проверки:**

- Источник молчит до заголовков: наступает таймаут, появляется состояние ожидания, выполняется повтор; после восстановления просмотр продолжается и индикатор исчезает.
- Источник зависает посередине ответа: ожидание чтения завершается таймаутом, повтор не повреждает данные/Range. Обрыв потока также не теряется как успешное завершение.
- Долгое исправное видео продолжает работать без общего короткого таймаута; обычная пауза/ожидание получателя не принимаются за отсутствие ответа источника.
- При смене видео или остановке нет позднего повтора старого файла, оставшегося spinner и незавершённых контекстов/таймеров.
- Ошибка источника, которую нельзя устранить повтором, отображается как ошибка, а не как бесконечное ожидание.

### R08 — P1. Первая запись может обогнать стартовую синхронизацию собственного журнала

**Требование:** перед первой записью после старта сверить собственный журнал с доступными пирами и догрузить недостающие операции. Это предусмотрено разделом 5.1 архитектуры и TASK-8 AC4. Решение A12 сохраняет возможность офлайн-записи: отсутствие пиров или их недоступность не должны навсегда блокировать работу.

**Причина:** в [node.go](../core/node/node.go), строки 283–288 и 352–362, стартовые подключения запускаются в горутинах, причём перед `replica.Pull` выполняется `announce`. Счётчик `pending` увеличивается только внутри `Pull` ([replica.go](../core/replica/replica.go), строка 227). До этого момента `Create` видит `pending == 0` и устанавливает `caughtUp = true` (строки 72–80). Последующая регистрация Pull уже не возвращает барьер: готовность однажды признана окончательной.

#### R08.1. Сценарий воспроизведения

Сценарий выведен из кода; в рамках ревью не запускался.

1. Локальная БД содержит собственный журнал до `seq = 10` под прежним ключом устройства. У известного доступного пира сохранены также операции этого автора 11 и 12.
2. Открыть Node и задержать ответ на стартовый `announce`, сохраняя доступность пира.
3. Сразу после открытия вызвать действие, создающее локальную операцию, например изменение выбора файлов. `Pull` ещё не зарегистрировал ожидание, поэтому запись проходит с `seq = 11` и другим содержимым.

#### R08.2. Предложенное исправление

### R09 — P3. Предложение сверять хеши транзакций при синхронизации

**Оценка после обсуждения:** приоритет снижен с P1 до P3. Это предложение дополнительной проверки для редкого аварийного сценария. Под транзакциями здесь понимаются подписанные операции реплицируемого журнала.

В штатной работе операции автора создаются только на его устройстве, а счётчик и новая операция сохраняются одной транзакцией SQLite. Другие устройства копируют подписанные операции, не меняя их содержимое. Архитектура также предусматривает ключ устройства без переноса через бэкап: восстановление на новом устройстве создаёт нового автора.

**Когда возможно расхождение:** локальная БД откатилась к старому состоянию, но прежний ключ автора сохранился; либо две независимо работающие копии используют один ключ. Например, телефон А создал операцию №12 и передал её телефону Б. Затем на А восстановили БД до №11 с прежним ключом и офлайн создали другую операцию №12. У А и Б теперь разные операции с одинаковыми `(author, seq)`, обе корректно подписаны. Это не следствие обычного обмена данными; сценарий требует отката БД с сохранением ключа либо нарушения уникальности экземпляра автора. Офлайн-запись после восстановления допускается решением A12, поэтому стартовая проверка из R08 не исключает такой случай полностью.

**Ограничение текущей реализации:** [replica.go](../core/replica/replica.go), строки 253–265, запрашивает только диапазоны из `vv.Missing`. Вектор версий содержит номера последних операций, но не их хеши. При одинаковом номере последней операции одного автора её содержимое не сравнивается. Если продолжение расходящейся цепочки не появится и не будет запрошено, форк может остаться необнаруженным, а данные на устройствах — различаться. Поэтому обещание A12 «форк потом будет обнаружен» для текущего протокола не гарантируется.

**Предложение:** при синхронизации сверять для каждого автора номер и хеш последней операции журнала. Разные хеши при одинаковом номере означают форк и должны приводить к предусмотренной ошибке `ErrFork`. Хеши операций с разными номерами напрямую не сравнивать как признак форка: разная длина журнала сама по себе является обычным отставанием. Автоматическое разрешение конфликта в предложение не входит.

**Недостающий тест:** соединить обычным протоколом два узла с одинаковыми векторами версий, но разными корректно подписанными последними операциями одного автора. Без новых записей и принудительной повторной отправки старых операций синхронизация должна обнаружить `ErrFork`, сохранив локальные журналы. Контрольные случаи: одинаковые операции не вызывают ошибку, а более короткий непротиворечивый журнал штатно догружается. Существующий `TestForkOfferedAtKnownSeq` в [replica_test.go](../core/replica/replica_test.go), строки 214–246, использует специальную повторную отправку старых операций и не проверяет самостоятельное обнаружение расхождения обычным протоколом.

Изменён только документ ревью. Предложение и тест описаны для последующей реализации; код, тесты и задачи не менялись, ничего не запускалось.

### R12 — P2. Убрать schema из операций; развивать протокол новыми типами и указывать версию приложения в Join

**Проблема:** общая константа `Schema` записывается во все новые операции в [op.go](../core/crdt/op/op.go), строки 105–113. [change.go](../core/crdt/op/change.go), строки 88–90, распознаёт только операции с равным ей значением. Простое увеличение константы делает неизвестными старому клиенту все новые операции, включая неизменившиеся типы, а новому клиенту — старые операции. После принятого Join неизвестные операции сохраняются и пересылаются, но не применяются к состоянию; первая неизвестная операция вместо распознаваемого Join отвергается валидатором и блокирует весь журнал автора. Это ограничение будущей совместимости, а не сбой между текущими клиентами со схемой 1.

**Согласованное решение:**

1. Убрать поле `schema` из создаваемых операций и общую проверку версии в декодере. Отдельную версию формата каждой операции также не вводить. Выбор обработчика определяется `type`; проверка подписи, последовательности, `prev` и членства сохраняется.
2. Существующим типам операций сохранять их смысл и формат. Совместимые дополнения допустимы через необязательные поля с определённым поведением при отсутствии; неизвестные поля игнорируются при применении. Для несовместимого изменения создавать новый тип операции, сохраняя обработчики старых типов для чтения истории. Идентификаторы типов и номера полей не переиспользовать.
3. Неизвестный тип после корректного Join сохранять и пересылать как исходные подписанные байты, не применяя к состоянию и не блокируя последующие известные операции. Первая операция по-прежнему обязана быть распознаваемым Join с корректным proof. Для будущего применения ранее неизвестных операций после обновления потребуется пересчёт соответствующей проекции из сохранённого журнала.
4. В Join добавить поле версии приложения (`AppVersion`) рядом с `Platform`. Это версия приложения, создавшего Join, а не версия Go-ядра или формата операции. Передавать её из приложения при создании Join и сохранять в данных участника вместе с именем и платформой, чтобы её можно было получить для диагностики. Добавленное поле входит в подписанные данные. Версия приложения не выбирает обработчик операции и не заменяет проверку членства.

**Граница сведений о версии:** Join записывается один раз, поэтому поле сообщает версию на момент вступления. После обновления приложения оно само не меняется. Чтобы в будущем определять именно текущую версию подключённого клиента, потребуется отдельная передача актуальной версии при подключении либо обновление данных участника; такой механизм в это решение пока не включён. Для старых Join без поля версия считается неизвестной, отсутствие поля не запрещает вступление.

**Переход формата:** уже подписанные операции не переписывать. Новый читатель может игнорировать прежнее поле `schema` как неизвестное, сохраняя исходные байты. Его CBOR-номер не занимать другим полем и не перенумеровывать оставшиеся поля. При этом текущий старый клиент, требующий `schema = 1`, новые операции без поля не распознает: удаление поля требует обновления клиентов, а не обеспечивает совместимость с прежним декодером автоматически.

**Проверки при реализации:** известные операции без `schema` принимаются и применяются; последовательность Join → неизвестный тип → известный тип сохраняется и передаётся без изменения байтов, последняя известная операция действует; версия приложения из Join доходит до данных участника, а старый Join без версии остаётся допустимым. Проверка подписей и proof не ослабляется.

**Предложенное поведение и границы исправления:**

1. Ошибки обработки данных перехватывать на уровне соответствующей записи или её поля. 2. Подготовка списка, группировка по дням и форматирование подписей должны продолжать работу с остальными элементами при ошибке одного файла. Общий `catch`, заменяющий всю хронологию сообщением об ошибке, требование не выполняет. Случай неизвестной даты должен корректно обрабатываться и при построении строк, включая первый элемент списка.
3. Ошибки рендера изолировать локальной React Error Boundary вокруг отображения записи, чтобы сбой дочернего компонента заменял только эту запись понятной заглушкой. Такая граница не перехватит ошибку подготовки списка в родителе, обработчика события или обычного асинхронного вызова: эти пути обрабатывать в месте выполнения. Один глобальный обработчик вместо защиты отдельных записей недостаточен. [Ограничения Error Boundary в документации React](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary).
4. Сохранить прокрутку, навигацию и работу с исправными файлами; в полноэкранном просмотре ошибка текущего файла не должна лишать возможности перейти к следующему или выйти. Проблему отображения не превращать в удаление файла или изменение выбора пользователя. Ошибка должна оставаться доступной для диагностики.
5. После исправления данных или смены отображаемого файла локальное состояние ошибки должно допускать нормальное отображение, а не оставлять вечную заглушку от предыдущей записи.

Остальные записи отображаются и открываются, навигация работает, а ошибка показана локально. Проверить ошибочную дату первым элементом списка и восстановление отображения после замены ошибочных данных корректными. Проверка должна охватывать пользовательский экран, а не только возврат значения из вспомогательной функции.

### R14 — P2. Отменять ненужные подключения и ограничить повторы линейным backoff

**Проблема:** [discovery.go](../core/node/discovery.go), строки 102–131, при Found добавляет адрес через `addPeer`, а при Lost удаляет только запись обнаружения. В [node.go](../core/node/node.go), строки 340–372, адрес сохраняется и получает цикл подключения, живущий до закрытия Node. Отдельной отмены кандидата нет; причина ошибки не влияет на повтор. Даже после ошибки `announce` запускается `Pull`, который снова подключается к тому же адресу. Это позволяет накапливать подключения к устаревшим или неподтверждённым адресам.

В [peer.go](../core/peer/peer.go) уже есть отдельные ошибки `ErrCertificate` и `ErrMembership`, но цикл подключения их не учитывает. При этом отказ удалённой стороны в подтверждении членства может выглядеть для клиента как EOF: сервер закрывает соединение без отдельного сообщения о причине. Такой результат нельзя надёжно отличить от сетевого обрыва только по EOF.

**Согласованная простая политика повторов:**

- Первая попытка выполняется сразу. После неё разрешены максимум **100 повторов** подряд при сетевых и неоднозначных ошибках: всего до 101 неудачной попытки в одной серии.
- Линейная пауза перед повтором с номером `n` равна `n × 10 мс`: 10, 20, 30, …, 1000 мс. Суммарно паузы составляют 50,5 секунды; длительность самих сетевых попыток в эту сумму не входит. Экспоненциальный backoff и дополнительный случайный разброс не вводятся.
- Явная ошибка сертификата или подтверждения членства завершает текущую серию сразу. После такой ошибки в `announce` не запускать `Pull`. Классифицировать ошибки по их типу/`errors.Is`, включая обёртки, а не по тексту сообщения. EOF сам по себе не считать явной ошибкой подлинности: он расходует обычный лимит повторов.
- Счётчик относится к последовательным неудачам подключения/синхронизации данного адреса в данном pile. После успешного раунда синхронизации серия неудач заканчивается; последующий разрыв начинает новую. Успех одного `announce` при постоянно неудачном `Pull` не должен бесконечно обнулять лимит.
- После исчерпания лимита завершать цикл и освобождать его ресурсы. Не создавать новую такую же серию автоматически по таймеру или при дублирующем Found; повторные объявления того же актуального кандидата также не должны создавать параллельные циклы. Новое обнаружение после исчезновения кандидата либо явная повторная попытка могут начать новую серию.

**Отмена:** у кандидата должен быть собственный отменяемый контекст, производный от контекста Node. Исчезновение объявления отменяет созданного им неподтверждённого кандидата, если других актуальных оснований держать этот адрес нет. Отмена прерывает сетевую попытку и ожидание backoff, не расходуя оставшиеся повторы. Закрытие Node отменяет все такие циклы. Один Lost не должен разрывать уже установленное соединение с подтверждённым участником. Остановка цикла сама по себе не удаляет участника из pile.

**Проверки при реализации:** точное число повторов и последовательность пауз; немедленная остановка на явной ошибке подлинности без последующего Pull; ограниченные повторы при EOF; отмена во время запроса и паузы; отсутствие параллельных циклов от повторных Found; сброс серии после успешной синхронизации и сохранение работающего соединения при Lost. Время и порядок событий задавать управляемо, без реального ожидания всех 100 пауз.

### R17 — Удаление файлов во время показа: баг P1 и фича-реквест P2

#### R17.1 — P1. Баг: неверная обработка удалённого текущего файла и пустого списка

**Проблема возникает даже после чтения актуальной хронологии.** В [session.go](../core/show/session.go), строки 83–96, обновление само перемещает курсор, если текущий файл исчез. Затем Next/Prev в [show.go](../core/show/show.go), строки 232–245, дополнительно сдвигает его. Например, было A, B, C, D, текущий кадр B; после удаления B нажатие Next сначала выбирает C внутри refresh, затем переходит на D. C оказывается пропущен.

Отдельный случай той же проблемы обработки результата: если удалены все файлы, refresh игнорирует пустую хронологию и оставляет прежний список, текущий кадр и количество файлов. Пустой результат не является ошибкой чтения и должен изменять состояние показа.

**Требуемое исправление:** обновление хронологии и команда перехода должны вместе выбирать корректную цель без непредусмотренного двойного перемещения. Если сессия ещё указывает на удалённый B, Next должен выбрать ближайший оставшийся следующий файл C. Аналогично Prev после удаления последнего текущего D должен выбрать C. Пустую хронологию нужно принять: состояние сессии не должно сообщать старый текущий файл, прежнее количество или продолжать его загрузку.

**Обязательно написать регрессионный тест.** Для основной ошибки достаточно одного тестового устройства, которое владеет файлами и является хостом. Использовать имеющиеся в [helpers_test.go](../core/show/helpers_test.go) подставную медиатеку, `newPhone`, `pileOf` и объявление экрана; проверять публичные методы Node/Host и возвращаемое состояние. Реальные телефон и телевизор, а также синхронизация между устройствами для этого теста не требуются.

1. Создать и опубликовать фотографии A, B, C, D с таким порядком в хронологии.
2. Запустить показ с B и проверить исходный текущий файл.
3. Исключить B через `Node.Decide(..., false)`, сохранив курсор сессии на B до следующей команды.
4. Вызвать `Host.Next()`.
5. Проверить, что текущий файл — C, индекс — 1, количество — 3. Проверять идентичность файла, а не только индекс: текущая ошибочная логика выбирает D.

Дополнить проверками Prev после удаления текущего последнего D и удаления всех файлов из активного показа. В последнем случае прежний кадр и количество больше не возвращаются, команды не приводят к выходу за границы списка. Конкретное продуктовое поведение пустого показа — завершение сессии или сохранение её с пустым экраном — пока не выбрано; ожидаемый результат этого варианта теста нужно уточнить вместе с решением.

**Порядок событий:** после появления автоматического обновления из R17.2 управляемо воспроизводить случай, когда удаление уже применено в БД, но сессия ещё указывает на B в момент Next. Использовать сигналы/барьеры, а не случайные задержки. Если сессия успела самостоятельно перейти на C до команды, Next на D корректен и не является воспроизведением этого бага.

#### R17.2 — P2. Фича-реквест: автоматически обновлять хронологию показа после удаления файлов

**Текущее поведение:** операция удаления может уже быть принята и применена в БД хоста, но сессия показа продолжает использовать старую копию хронологии. Refresh вызывается из Next, Prev и Goto; State, Play и Pause список не перечитывают. Периодический tick загрузчика обновляет доступность источников и планирование по прежнему списку. Получение новой операции само по себе не обновляет хронологию активной сессии.

**Запрос:** после применения удаления на хосте автоматически обновлять список показа, его состояние и список для загрузки, без нажатия кнопок и перезапуска показа.

**Требуемое поведение:**

- Если удалён другой файл, текущая фотография остаётся текущей по своему ID; количество, индекс и дальнейшая навигация соответствуют новому списку. Удалённый файл исключается из последующих загрузок и переходов.
- Если удалён текущий файл, показ выбирает ближайший оставшийся следующий файл, а при его отсутствии — предыдущий. Renderer получает переход на выбранный файл; последующие команды работают с обновлённым курсором без лишнего сдвига из R17.1.
- Если файлов не осталось, хост сообщает об отсутствии файлов и текущего кадра, прекращает загрузку и воспроизведение удалённого медиа. Окончательный вид пустого показа определяется вместе с R17.1.
