## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Показ ведёт один узел — хост; экран общается только с ним, а хост сам ходит к источникам. Сессия показа живёт только на хосте и в CRDT не попадает. Пользователь должен понимать, какие экраны доступны и почему некоторые недоступны (architecture.md, 2.2 и 2.3).
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Go-часть (сессия показа на хосте):
1. Пакет core/show: Host с одной активной сессией в памяти (D8). Start(pile, screen, [asset]) — экран из node.Screens(); недоступный экран (AirPlay не с iPhone) — ошибка с пояснением экрана; Cast — подключение core/cast; AirPlay на iPhone-хосте — сессия без Go-рендерера (рисует натив, TASK-18). Курсор по хронологии, next/prev/goto, play/pause для видео, stop.
2. Медиа для экрана: отдельный HTTP-listener на LAN только на время сессии, маршрут /show/{token}/{asset}/{revision}/{2|3}; токен случайный на сессию, отзывается при остановке; T2 — из blob-хранилища хоста или от владельца (node.Blob), T3 — только для видео, стрим с источника через хост с Range (новый node.ServeOriginal). Других маршрутов нет.
3. Прогретый кеш: core/prefetch на курсоре сессии; SetItems из хронологии, Loaded для T2 уже в хранилище (node.Cached), SetOnline по живому pull-соединению с владельцем (node.Online), Plan после каждого события и раз в секунду; загрузка T2 через node.Blob, вытеснение node.Evict; ждущие элементы — в состоянии сессии.
4. Cast: LOAD текущего элемента (image/jpeg для фото, mime для видео) при старте и на каждой смене курсора, PLAY/PAUSE командой, STOP при остановке; ошибки LOAD и обрыв — в состоянии и в журнале диагностики (renderer).
5. HTTP API для UI: POST/GET/DELETE /show, POST /show/next|prev|goto|play|pause; api/openapi.yaml.
6. Тесты: два узла и хост на каждом, фейковый Cast receiver, токен экрана, видео с Range, окно кеша, вытеснение, офлайн-источник, ошибки Cast. gofmt, go vet, go test -race, make check.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Начата Go-часть: сессия показа на хосте, раздача медиа экрану, встраивание планировщика кеша (TASK-15) и управление Cast (TASK-17). Интерфейс выбора экрана и пульта — следующим шагом.

Go-часть сделана (коммиты 80c7bfe, 4749140), интерфейс выбора экрана и пульта — за UI.
- Пакет core/show: Host (show.New(node, budget), DefaultBudget = 1 ГиБ) с одной сессией в памяти; Start(pile, screen, asset?) останавливает идущий показ; Next/Prev (на краях стоит), Goto(asset), Play/Pause (только видео, иначе ErrNotVideo), State, Stop (идемпотентен). Хронология перечитывается на каждом шаге курсора — файлы, пришедшие во время показа, появляются после следующей команды.
- Экран: из node.Screens(); недоступный — UnavailableError с пояснением экрана (AirPlay не с iPhone); Cast — подключение core/cast; AirPlay на iPhone-хосте — сессия без Go-рендерера (курсор и кеш в Go, рисует натив, TASK-18).
- Медиа для экрана: на время Cast-сессии отдельный plain HTTP listener на локальном адресе соединения с Cast (порт случайный), единственный маршрут GET /show/{token}/{asset}/{revision}/{2|3}; токен — rand.Text() на сессию, отзывается остановкой или новым стартом (403 на чужой токен). 2 — T2 (image/jpeg) из blob-хранилища хоста или от владельца; 3 — только для видео, оригинал стримится с источника через хост с Range (node.ServeOriginal). UI- и peer-маршруты токену экрана недоступны (проверено тестом).
- HTTP API UI: POST /show {pile, screen, asset?} → 201 состояние; GET /show; DELETE /show → 204; POST /show/next|prev|play|pause, POST /show/goto {asset}. Ошибки: no_show, unknown_screen, screen_unavailable (+reason), empty_pile, not_video, screen_unreachable, unknown_pile, unknown_asset. httpapi.WithNode теперь принимает *show.Host; мобильный фасад создаёт и останавливает его сам, экспортируемый API фасада не менялся.
- Решения на ревью: токен живёт до конца сессии без TTL; быстрые шаги курсора склеиваются — экран получает LOAD только последнего файла; автоматического переподключения к Cast нет (ошибка disconnected до перезапуска показа, перезапуск с текущего файла — POST /show с asset).

Go-часть влита в master, решение A24 записано. AC #1 и #3 доказаны тестами; #2 (управление с экрана хоста) и #4 (список экранов с причинами в UI) — ждут интерфейса. Пульт с других телефонов на этапе 1 не делаем (этап 2).

Интерфейс показа (ветка show-ui, приложение):
- «Показать на экране» в pile и в полноэкранном просмотре (старт с открытого файла, asset). Экран ScreenPicker: GET /screens, pull-to-refresh, доступный экран — кнопка (Google Cast / AirPlay), недоступный — строка с именем и причиной ядра как есть, без кнопки; пустой список объясняет, что проверить. Ошибки старта: screen_unavailable — reason как есть, screen_unreachable — «Экран не ответил…».
- Экран Remote (пульт на хосте): опрос GET /show раз в секунду, команды next/prev/play/pause обновляют состояние из ответа; превью T2 текущего файла через /piles/{pile}/blob/.../2 с thumbhash из хронологии; «n / всего», автор (author → author_name из хронологии), время; Пауза/Воспроизвести только при kind == video; ошибки экрана по коду на русском (load_failed, command_failed, playback_failed, disconnected, иначе «Ошибка экрана: <code>»), после disconnected — «Перезапустить показ» = POST /show с тем же экраном и asset = current.id; баннер ожидания по авторам waiting; «Остановить показ» = DELETE /show и возврат туда, откуда начали (pile или просмотр).
- Решения: выбор экрана заменяется пультом в стеке маршрутов; на пульте нет «Назад», аппаратная «Назад» не уводит с пульта — выйти можно только остановкой (иначе показ продолжался бы без пульта). Баннер без склонения имени: «Ждём iPhone: Аня» / «Ждём телефон: Боря» (платформа — по имени участника pile), т.к. имена — свободный текст и родительный падеж («iPhone Ани») надёжно не построить.
- Тесты app/test/show.test.tsx (12) против фейкового ядра.
