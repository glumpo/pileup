## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Транспорт загрузок у владельцев использует MaxIdleConnsPerHost по умолчанию (2), а параллельных запросов к одному владельцу 5–10, поэтому лишние TLS-рукопожатия повторяются. cache.db открыт с synchronous=FULL: на каждую публикацию fsync WAL под общим мьютексом кеша, хотя кеш сверяется с диском при открытии. «Мелкое» в doc/architecture-review.md.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Тесты (коммит 365edb1), на коде до изменения:
- TestParallelFetchesFromOwnerReuseConnections (core/node/owner_test.go, красный): `3 new connections to the owner for the next 5 parallel downloads, want none` (3 из 3 прогонов) — после 5 параллельных T2 транспорт держит 2 простаивающих соединения, следующая серия открывает 3 новых. Соединения считает слушатель поддельного владельца (11 фото, T2 отвечает за 200 мс, чтобы загрузки шли одновременно).
- TestCacheIsConsistentAfterLosingLastCommits (core/blob/blob_test.go, зелёный и до изменения): снимок cache.db и WAL после публикации x; затем публикация y и снятие x; база возвращается к снимку (как потеря последних транзакций при обрыве питания), а на диске файл y есть, файла x нет. После открытия ничего не удерживается и лишних файлов нет, y загружается заново. Отдельно проверено (временный тест), что такой снимок действительно содержит x. Значение synchronous — настройка соединения, в файл базы не записывается, поэтому само NORMAL снаружи не наблюдается; тест страхует его последствия.

Сделано (974ac6e):
- owners(): http.Transport{MaxIdleConnsPerHost: 8} (как предлагало ревью; параллельных запросов к одному владельцу 5–10: загрузчик показа до 5, фоновые T1 до 5, viewer, экран).
- blob.Open: _pragma=synchronous(NORMAL) вместо FULL.
- doc/adr/cache.md: §2, §5.1 (соединения), §5.7 (обрыв питания), §7 инвариант 5, §10.

Замер (временный тест вне коммитов, x86, без -race): публикация 600 T1 по 20 КБ, лучший из 3 — FULL 3,34 с, NORMAL 1,99 с.

Проверка: TestParallelFetchesFromOwnerReuseConnections -count=5 -race — ok; go test -race ./... в core — ok.

Оставшиеся ограничения: больше 8 одновременных запросов к одному владельцу по-прежнему открывают лишние соединения; простаивающие соединения живут без IdleConnTimeout (закрываются при смене адреса владельца, при обрыве и при закрытии узла), у владельца их держит http.Server (IdleTimeout 20 с). С NORMAL после обрыва питания могут пропасть последние удержания и закрепления (закрепления — в той же базе): файлы загрузятся заново, а закрепление, сделанное за секунды до обрыва, придётся повторить.

Решение для architecture.md: транспорт к владельцам держит до 8 простаивающих соединений на владельца — столько параллельных запросов к одному владельцу бывает (загрузчик показа, фоновые T1, viewer, экран), и серия загрузок не повторяет TLS-рукопожатия. cache.db открыт с synchronous=NORMAL: в WAL обрыв питания теряет только последние транзакции, а сверка базы с диском при открытии убирает объекты без файлов и файлы без объектов; публикация стоит один fsync (файла) вместо двух под мьютексом кеша.

Уточнение: простаивающее соединение закрывает сам владелец через 20 с (IdleTimeout его http.Server), поэтому переиспользование работает между сериями загрузок, идущими чаще раза в 20 с (показ, прокрутка сетки); после более долгой паузы первая серия снова открывает соединения.
