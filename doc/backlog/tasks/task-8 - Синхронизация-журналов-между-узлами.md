## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Метаданные pile (участники, файлы) должны оказаться у всех участников, как бы и в каком порядке узлы ни встречались. Обмен идёт по version vectors, ответ строго по порядку seq, так что на узлах всегда хранится непрерывный префикс журнала каждого автора (architecture.md, 5.1).
<!-- SECTION:DESCRIPTION:END -->

- [x] #2 Операции чужого автора, полученные через третий узел, принимаются и проверяются по подписи автора
- [x] #3 После разрыва и повторного соединения передаются только недостающие операции
- [x] #4 Перед первой записью после старта узел сверяет свой seq с пирами и догружает собственный журнал, если у пиров он длиннее

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. В core/store добавить VV() (version vector без всей проекции) и ID(author, seq) (id сохранённой операции для проверки форка); тесты → verify: go test ./store/
2. Пакет core/replica (имя sync занято stdlib): Node поверх store; сервер — HTTP поверх peer: GET /vv (VV сразу), POST /vv (long-poll: ответ, когда у сервера появилось то, чего нет у клиента, или по таймауту), GET /ops?author=&from= (операции автора по порядку seq, CBOR-последовательность байтовых строк)
3. Pull(ctx, addr): дозвон через peer.Dial, раунд = VV пира → vv.Missing → /ops по каждому автору → store.Apply; дальше long-poll. Каждый узел сам тянет у каждого пира
4. Форк: ErrPrev на seq > 1 или операция с уже известным (author, seq) и другим id → ErrFork; не разрешаем
5. Create: перед первой записью после старта ждём, пока все активные Pull завершат первый раунд (или упадут); если активных Pull нет — пишем сразу
6. Тесты по критериям: сходимость двух узлов и доставка новых операций, ретрансляция через третий узел (честная и с подменой байтов), повторное соединение — передаются только недостающие (счёт операций в ответах), восстановление из старой копии БД без форка и контрольный форк без догрузки
7. gofmt, go vet, go test -race, make check

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Пакет core/replica (имя sync занято stdlib): Node поверх store.Store — New, Handler, Serve, Pull, Create; ErrFork. В store добавлены VV() и ID(author, seq) (покрыты property-тестом).
Решения, требующие ревью:
- Протокол — HTTP/1.1 поверх peer.Conn. GET /vv — VV сервера сразу (CBOR-map author(bstr 32) → seq). POST /vv с телом VV клиента — long-poll: ответ, как только у сервера есть операции, которых нет у клиента, иначе через 20 с. GET /ops?author=<hex>&from=<n> — все операции автора с seq ≥ n по порядку, CBOR-последовательность байтовых строк (каждая — операция байт-в-байт). Батчей нет: ответ — весь хвост, клиент применяет по одной по мере чтения, поэтому оборванный ответ не теряет уже применённое.
- Pull-модель: каждый узел сам вызывает Pull к каждому известному пиру и сам решает, что тянуть (vv.Missing); сервер ничего не шлёт без запроса. Для двусторонней сходимости оба узла тянут друг у друга (два TCP-соединения).
- Новые операции после соединения: long-poll, сервер будит ожидающих при Create и при применении чужих операций (gossip идёт дальше сразу). Таймауты: ожидание 20 с, запрос клиента 40 с, ReadHeaderTimeout/IdleTimeout сервера 20 с. Pull возвращает ошибку при любой ошибке сети или протокола; переподключение — забота вызывающего.
- Форк — ErrFork (с автором и seq): ErrPrev для seq > 1 (подписанная автором операция N+1 ссылается на другую N) или операция с уже имеющимся (author, seq) и другим id. Не разрешается; поток этого ответа обрывается, остальные авторы раунда догружаются, Pull завершается с ошибкой. Совпадающие повторы молча пропускаются.
- Догрузка своего журнала: Create перед первой записью после старта ждёт, пока каждый активный Pull закончит первый раунд (сверка VV и загрузка всего недостающего, включая свой журнал) или завершится ошибкой. Если активных Pull нет или пиры недоступны — пишем сразу (local-first: запись без сети обязана работать); риск форка при восстановлении из старой копии БД принимается, форк потом обнаруживается как ErrFork. После первой записи ожидания нет.
- Serve пускает только участников этого pile (listener с одним секретом); Handler сам pile не проверяет — один порт на pile, как в TXT mDNS (7.1).
Тесты: сходимость двух узлов и доставка новых операций, ретрансляция через третий узел (честная и с подменой байтов → op.ErrSignature), повторное соединение (подсчёт операций в ответах /ops), восстановление из старой копии с догрузкой (seq 5, prev = op 4), запись без пиров и контрольный форк, форк на известном seq, игнорирование повторов, отсутствие запросов на простаивающем соединении. Мутационная проверка: снятие каждой проверки ловится тестом.

Проверка владельцем: тесты, go vet и make check проходят; влито в master (3a45789). Решение A12 записано в architecture.md.
Риски: (1) при односторонней достижимости (например, вход по адресу из QR без mDNS) сходится только сторона, которая может дозвониться — нужен обратный канал или встречное подключение; (2) участник, объявляющий VV, который не может отдать, вызывает холостой цикл; (3) сервер грузит весь хвост автора в память; (4) после форка перезапущенный Pull снова упрётся в тот же форк.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Пакет core/replica: синхронизация журналов pile по HTTP/1.1 поверх core/peer. Сервер отдаёт version vector и упорядоченные операции любого автора с заданного seq, long-poll будит клиентов при новых операциях. Клиент тянет недостающее и применяет через store. Обнаружение форка (ErrFork), догрузка собственного журнала перед первой записью. В store добавлены VV() и ID(author, seq).
Проверка: тесты на схождение, пересылку через третий узел (подмена байтов отвергается), передачу только недостающего после переподключения (подсчёт отданных операций), восстановленный узел без форка, форк. Решение на ревью: A12; риски в заметках.
