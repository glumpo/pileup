## Description

<!-- SECTION:DESCRIPTION:BEGIN -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Красные тесты (b6dee8b, app/test/viewer.test.tsx): 5 из 5 падали на поведении, tsc чистый.
- «a page shows the thumbnail instead of the thumbhash while the display version loads»: на странице оставался thumbhash — `expect(viewer().queryAllByTestId('placeholder')).toEqual([])` получил `[<Image testID="placeholder" …>]`; T1 на странице не было.
- «a page of a member who does not answer says so and loads by itself once the member is back»: `Unable to find an element with text: Нет ответа от участника: Боря. Возможно, погас экран — попросите разблокировать телефон и открыть Pileup.`
- «a page says so when the file was removed / the core failed / the file cannot be shown»: `Unable to find an element with text: Файл удалён или изменён: обновите хронологию` / `Не удалось загрузить файл. Ошибка ядра: internal` / `Не удалось показать файл`.

Фикстура. В viewer.test.tsx Image из react-native подменён обёрткой над моком пресета: при монтировании и смене uri она делает fetch(source.uri, {headers}) в фейковое ядро и вызывает onLoad, если ответ 200 с телом «JPEG», иначе onError — как нативный Image, который статуса не сообщает. Тесты видят только текст на странице и запросы к ядру: как приложение узнаёт причину и как повторяет, им неизвестно. fakeCore принимает ответ-обещание (T2 «грузится»), тип Reply экспортирован. Остальные тесты не менялись.

Реализация (ffedc41). Viewer.tsx: страница — Preview(thumbhash, T1) на всю страницу и поверх неё Image T2 (testID image, как раньше). Image onError → api.checkBlob (новый метод api.ts: GET того же URL с Bearer, при не-2xx бросает ApiError с кодом ядра, как call). source_unavailable → подпись «Нет ответа от участника: <author_name>. Возможно, погас экран — попросите разблокировать телефон и открыть Pileup.» внизу страницы и через 2 с перемонтирование Image (key), пока не будет onLoad; при новой ошибке — снова проверка; подпись остаётся до загрузки. unknown_asset → «Файл удалён или изменён: обновите хронологию»; прочие ошибки → «Не удалось загрузить файл. <describe>»; проверка ответила 200 (Image не смог показать ответ) → «Не удалось показать файл»; без повтора. Preview, сетка и пульт не менялись.

Почему GET после ошибки. onError в RN даёт только строку платформы, без статуса и кода. Варианты: fetch вместо Image — T2 шёл бы в JS-память при каждом просмотре и всё равно грузился бы Image второй раз; HEAD — маршрут GET в Go отвечает и на HEAD, но тело с кодом ошибки отбрасывается, а ядро всё равно загружает файл, выигрыша нет; отдельный маршрут статуса в ядре — новая поверхность API ради одного экрана. GET того же URL видит то же, что Image, код берётся из тела, ошибка описывается как у остальных вызовов (ApiError, describe). Запрос идёт только после ошибки: успешная страница стоит одного запроса.

Почему так повторяем. 2 с — «раз в несколько секунд» из Н5: подписки «участник снова в сети» в API нет (Н9, TASK-39), локальный запрос к ядру почти ничего не стоит, владелец подхватывается в пределах 2 с после ответа. Повтор только для source_unavailable: unknown_asset постоянен, 500 — «битый» T2 (TASK-37), 200 при ошибке Image — не декодируется, повтор крутился бы без конца. «участника», а не «телефон/iPhone», как на пульте: у элемента хронологии нет платформы, а сопоставление имени с pile.members ненадёжно (имена могут совпадать).

Проверка: `npx tsc --noEmit` — чисто; `npx jest --ci` — 9 наборов, 51 тест, все прошли, предупреждений в консоли нет. Мутация: с retry: false для source_unavailable тест повтора падает (`Expected: > 2, Received: 2`).

Ограничения.
- Проверочный GET заново запускает загрузку у владельца. Если адрес владельца ещё считается рабочим, а телефон молчит, подпись появляется через два таймаута ядра (до 2×20 с), и каждая попытка повтора тоже ждёт до 20 с.
- Гонка: если владелец ответил между ошибкой Image и проверкой, страница скажет «Не удалось показать файл» без повтора; помогает закрыть и снова открыть просмотр.
- Повторяет каждая смонтированная страница (текущая и соседние в окне FlatList), пока она смонтирована; закрытие просмотра их останавливает.
- T1 остаётся под загруженным T2 (пропорции одинаковые, T2 его закрывает).
- Курсора и Protect для viewer в ядре по-прежнему нет (Н5 п. 3) — вне задачи. doc/adr не менялся: документа по UI приложения нет, ядро и API не менялись.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Полноэкранный просмотр: страница показывает thumbhash, затем T1 из кеша, поверх — T2. Если T2 не загрузился, приложение повторяет GET того же URL (api.checkBlob), чтобы узнать код ядра: при 502 source_unavailable подпись «Нет ответа от участника: <имя>. Возможно, погас экран — попросите разблокировать телефон и открыть Pileup.» и перезапрос раз в 2 с до успеха; unknown_asset, прочие ошибки и неразборчивый ответ — понятный текст без повтора. Сетка и пульт не менялись. Проверка: красные тесты app/test/viewer.test.tsx (Image подменён загрузчиком через фейковое ядро) падали 5/5, теперь tsc чистый, jest 51/51. Ограничения: проверочный GET повторяет загрузку у владельца (первая подпись до 2×20 с, если адрес ещё считается рабочим); курсора у viewer в ядре нет (Н5 п. 3).
