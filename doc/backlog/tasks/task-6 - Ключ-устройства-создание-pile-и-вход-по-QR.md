## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Регистрации нет: участник определяется ключом устройства, а членство в pile — знанием секрета из QR-приглашения (architecture.md, раздел 7). Ключ не должен уходить в бэкап, иначе восстановленное приложение продолжит чужой журнал и создаст форк.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
План покрывает только Go-часть (нативное хранение ключа в Keychain/Keystore и экран QR — вне этого плана).
1. core/device: интерфейс хранилища ключа (Load/Save seed), Key() — создать ed25519 при первом использовании и загружать потом; файловая реализация для десктопа и тестов → тест: ключ создаётся один раз и перезагружается, новое хранилище — новый автор.
2. core/invite: компактный версионированный формат приглашения для QR (pile_id, секрет, адреса пригласившего) → тесты: round-trip, отказ на битых строках и неизвестной версии.
3. core/node: узел устройства — ключ, список pile с секретами и пирами в каталоге данных, создание pile (Join, затем PileCreate), приглашение, вход по приглашению (проверка секрета подключением к пригласившему, Join, синхронизация); один listener на pile поверх core/replica; тянущая сторона сообщает свой порт, и пригласивший начинает тянуть у новичка → интеграционные тесты на трёх узлах через loopback, поддельное приглашение, обе стороны как пригласивший, переживание перезапуска.
4. core/httpapi + api/openapi.yaml: создание pile, список, приглашение, вход по приглашению под токеном → HTTP-тесты.
5. gofmt, go vet, go test -race, make check.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Начата Go-часть: формат приглашения, создание pile и вход в ядре, HTTP API для UI. Нативное хранение ключа (Keychain/Keystore) и экран QR — позже.

Go-часть сделана (нативные Keychain/Keystore и экран QR — нет):
- core/device: интерфейс Keystore{Load() (seed, error); Save(seed) error} (пустой seed = ключа нет), Key(ks) создаёт ed25519 при первом использовании и загружает потом; повреждённый ключ (не 32 байта) — ошибка ErrSeed, а не тихая замена (иначе новый автор). File(path) — файловая реализация (0600, атомарная запись) для десктопа и тестов. Интерфейс совместим с gomobile, чтобы Swift/Kotlin реализовали его поверх Keychain (ThisDeviceOnly) и Keystore (без бэкапа).
- core/invite: строка "PILEUP:" + base32 (RFC 4648, верхний регистр, без паддинга) от байта версии (1) и CBOR-массива [pile_id, secret(32), [addr...]], адрес — netip.AddrPort.MarshalBinary (IPv4 6 байт, IPv6 18 байт). Весь текст в алфавите QR alphanumeric; 3 адреса — 147 символов. Неизвестная версия — ErrVersion, остальное — ErrFormat.
- core/node: узел устройства. Каталог данных: device.key (на десктопе), piles.json (id, secret, port, peers каждого pile; 0600), piles/<hex id>.db (SQLite на pile, A9). pile_id — 16 случайных байт, секрет — 32. Один TCP-listener на pile (на всех интерфейсах), порт сохраняется и переиспользуется после перезапуска, если занят — новый. Создатель пишет Join, затем PileCreate. Вход: разбор приглашения, проверка секрета подключением peer.Dial к адресам пригласившего по очереди (первый принявший адрес становится пиром; неверный секрет или недоступность — ErrUnreachable, ничего не создаётся), затем Join в новом store и синхронизация.
- Как пригласивший узнаёт новичка: тянущая сторона перед каждым (пере)подключением шлёт POST /announce?port=<свой порт> на том же peer-сервере pile; сервер берёт IP из соединения, добавляет IP:port в пиры pile (сохраняет) и начинает тянуть оттуда. Так тянут обе стороны, и это переживает перезапуск и смену порта. Третий участник получает журналы остальных через пригласившего (relay).
- core/httpapi: WithNode(token, node) — GET /piles, POST /piles, GET /piles/{id}/invite, POST /piles/join; все маршруты под токеном; ошибки — {"error": код}. New(token) оставлен для мобильного фасада. api/openapi.yaml обновлён.
- Риски: повтор pull к недоступному адресу раз в секунду без нарастающей паузы; список пиров только растёт (смена IP по DHCP добавляет адреса); если после записи Join старт pile упал, файл БД остаётся, и повторный вход по тому же приглашению упрётся в ErrJoin; гонка двух одновременных Join одного pile не исключена; адреса для приглашения поставляет вызывающий (Config.Addrs) — на мобильных это будет NetworkInfo, сейчас ни мобильный фасад, ни pileupd узел не запускают.
