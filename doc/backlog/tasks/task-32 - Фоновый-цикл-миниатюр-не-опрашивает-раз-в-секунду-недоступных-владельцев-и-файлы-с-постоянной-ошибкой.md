## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Проход фоновых T1 читает всю проекцию, снимает удержания и вызывает open для T1 каждого чужого файла, в том числе кешированных (замер на x86: ~0,1 с на 600 файлов, на телефоне в разы дольше). Если хоть одна загрузка не удалась, проход повторяется через 1 с — пока у недоступного участника есть незагруженный T1 или пока в pile есть файл с постоянной ошибкой. Такой файл каждый участник запрашивает раз в секунду, и владелец каждый раз пытается его отрендерить, занимая очередь рендера. Н8 в doc/architecture-review.md.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Красные тесты (core/node/thumbnails_test.go, коммит d415a18; заготовка brokenPause и SetBrokenPause), на коде до исправления:
- TestUnavailableOwnerIsAskedForThumbnailsWhenItConnects/never_connected: `3 thumbnail requests to an owner that never connected, want at most 1`;
- …/gone_asleep: `2 thumbnail requests while the owner is away, want at most 1` (2–3 в разных прогонах);
- TestThumbnailOwnerDoesNotServeIsAskedAgainOnlyAfterPause/not_found: `thumbnail asked again 10.73655ms after the owner answered 404, want not before the pause of 3s`; …/render_error: то же для 500;
- TestPassWithEveryThumbnailCachedTouchesNeitherOwnersNorCache: `pass after a pile change with every T1 cached: 1 cache holds taken, 1 requests to the owner; want none and the first one` — к владельцу проход и раньше не шёл, а удержание в кеше брал по каждому файлу.
Попытки загрузки считаются по журналу диагностики участника (события «fetch …» с ключом владельца) и по запросам на поддельном владельце; обращения к кешу — триггером BEFORE INSERT ON holds в blobs/cache.db (каждое попадание в кеш берёт удержание, cache.md §3). Таймаут заголовков в журнал не попадает (download отменяет контекст, report пропускает context.Canceled), поэтому в «gone asleep» владелец обрывает ответ, а не молчит.

Сделано (f3d86db):
- fetchThumbnails: Retain, затем один Held(pile, T1) и Online; через open запрашиваются только недостающие T1 чужих файлов владельцев из Online, не стоящих на паузе.
- Пробуждение: изменение реплики и таймер. Отдельный сигнал о подключении не понадобился: Pull в начале каждой сессии вызывает track(1) → notify, а learn (участник в Online) идёт до Pull. Проверено: тесты «после подключения T1 загружается» проходят без отдельного сигнала (первая версия с каналом в pile убрана как лишняя).
- Таймер: 1 с — если у владельца из Online загрузка упала с ErrUnavailable без ErrRefused; иначе brokenPause (5 мин), если есть файлы на паузе; иначе таймера нет.
- Пауза файла: любая другая ошибка (404 → ErrUnknownAsset, другой статус → ErrRefused) — файл не запрашивается brokenPause, затем первый проход запрашивает снова. Паузы в памяти цикла.
- doc/adr/cache.md: §2, §5.1 (таблица исходов), §5.5, §8, §10.

Замер (временный внутренний тест вне коммитов: pile с 600 чужими T1 в кеше, лучший из 10 проходов fetchThumbnails, x86, без -race): до — 224,9 мс на проход (View 5,7 мс), после — 12,0 мс (View 5,9 мс).

Проверка: новые тесты -count=5 -race — ok; go test -race ./node ./show ./httpapi ./mobile — ok.

Оставшиеся ограничения: владелец, достижимый для загрузки, но без живого исходящего соединения синхронизации (только входящее), фоново свои T1 не отдаёт; после входа по приглашению T1 пригласившего грузятся после первого announce к нему, а не сразу. Владелец из Online, у которого загрузки падают с ErrUnavailable (уснул, а соединение синхронизации ещё живо, до ~40 с), по-прежнему опрашивается раз в секунду. Паузы «битых» T1 сбрасываются перезапуском. Таймаут заголовков при загрузке не пишется в диагностику (отдельная находка, не в этой задаче).

Решение для architecture.md: фоновый цикл миниатюр запрашивает только недостающие T1 (одна выборка удерживаемых вместо обращения к кешу по каждому файлу) и только у владельцев с живым соединением синхронизации; подключение участника будит цикл, потому что начало сессии синхронизации — изменение реплики. Файл, T1 которого владелец не отдал (404 или ошибка рендера), стоит на паузе 5 минут в памяти и затем перепроверяется; таймер раз в секунду остался только для владельца на связи, у которого загрузка не удалась. Так недоступный участник и битый файл не заставляют всех повторять проход и рендер у владельца каждую секунду.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Фоновый цикл миниатюр больше не опрашивает раз в секунду: проход берёт удерживаемые T1 одним Held и запрашивает только недостающие T1 владельцев с живым соединением синхронизации (Online); вернувшийся владелец будит цикл через изменение реплики в начале сессии синхронизации. Файл, на T1 которого владелец ответил 404 или ошибкой, стоит на паузе 5 мин и затем перепроверяется; таймер 1 с остался только для владельца на связи с неудачной загрузкой. Проход по 600 кешированным T1: 225 → 12 мс (x86). Все поведения сначала воспроизведены красными тестами в core/node/thumbnails_test.go (обращения к кешу — триггером в cache.db); go test -race ./node ./show ./httpapi ./mobile проходит. doc/adr/cache.md обновлён. Ограничения: владелец только с входящим соединением фоново T1 не отдаёт; владелец на связи с падающими загрузками опрашивается раз в секунду, пока соединение не порвётся.
