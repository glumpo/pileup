## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Адреса участников хранятся в piles.json (Peers) без привязки к устройству и только добавляются. Если у телефона сменился адрес (DHCP, другая сеть, занятый порт), узел продолжает подключаться к старому: серия повторов до исчерпания, при каждом старте заново, барьер первой записи ждёт её первую попытку. Ответ на announce отдаёт все когда-либо виденные адреса, поэтому старый адрес расходится всем участникам и возвращается после удаления. У одного участника бывает несколько рабочих адресов (IPv4 и IPv6 из приглашения, Wi-Fi и точка доступа), а узел может получить в списке собственный адрес и подключиться сам к себе. По журналу диагностики сейчас нельзя понять, какое устройство по какому адресу отвечает и откуда качаются его файлы. Без этой задачи нельзя сделать повторы подключения бесконечными (Н1 в doc/architecture-review.md): мёртвые адреса опрашивались бы вечно. Решение согласовано в обсуждении ревью архитектуры 2026-11-10: адреса вне журнала операций (A18), ключ, ответивший на адресе, хранится рядом с адресом, ответ на announce содержит пары ключ-адрес, совместимость со старым форматом ответа не нужна (A31: устройства обновляются вместе).

2. piles.json: необязательное поле keys (адрес → ключ). В памяти pile.keys; пишут: подтверждение своим announce и вход по приглашению — всегда; входящий announce и список из ответа — только если адрес ещё ничей.
3. У цикла флаг live (успешный announce, идёт Pull). Правило: адрес вытеснен, если его участник live на другом адресе, а сам адрес не live. Проверка — при подтверждении участника, после неудачной попытки и при разборе списка из ответа. Вытеснение отменяет цикл, удаляет адрес из Peers и keys, при необходимости переводит адрес загрузки на рабочий.
4. Ответ на announce: [{key hex, addr}] из Peers с известным ключом, без ключей спрашивающего и своего. Ключ спрашивающего берётся из peer.Conn через ConnContext. Announce от самого себя ничего не добавляет.
5. Журнал диагностики (Discovery): имя и 8 hex ключа (store.Member), адрес в поле peer.
6. Документы: security.md §4.2, cache.md §5.1.1 и §8, решение A35, пометки в architecture-review.md. gofmt, vet, тесты с -race, make check.

7. Найдено при реализации: replica.Pull через keep-alive переподключался к другому устройству на том же адресе без нового announce. Pull запоминает ключ первого соединения и завершается с ErrPeerChanged при другом ключе; тест в core/replica/device_test.go.

Реализация: piles.json получил необязательное поле keys (адрес → ключ), в памяти pile.keys. Ключ пишут: подтверждение своим announce и вход по приглашению — всегда; входящий announce и список из ответа — только для адреса без ключа. У цикла флаги live (идёт Pull) и failing (последняя попытка неудачна). Адрес вытесняется (удаление из peers и keys, отмена цикла), когда его участник live на другом адресе, а сам адрес не live и (failing или без цикла). ## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Адреса участников хранятся в piles.json в обязательном поле peers «адрес → ключ устройства, которое там отвечает». Ответ на announce передаёт пары «ключ, адрес» без адресов спрашивающего. Неработающий адрес участника, подключённого по другому адресу, вытесняется (в том числе сохранённый до перезапуска), а загрузка его файлов переходит на рабочий адрес. Несколько рабочих адресов одного участника остаются. Собственный адрес не подключается. Синхронизация завершается, если по тому же адресу ответило другое устройство. Каждое изменение таблицы адресов пишется в журнал диагностики с именем и ключом участника. Решение A35; обновлены doc/adr/security.md (§4.2, §4.5, §5.1), doc/adr/cache.md (§5.1.1, §8, §10), пояснения в doc/architecture-review.md.
Проверка: каждое поведение сначала красным тестом на старом коде, затем зелёным; go test -race ./..., 10 прогонов адресных тестов под -race, make check — зелёные.
Риски: piles.json прежнего формата не открывается (решение владельца: совместимость в MVP не нужна) — на устройствах с данными прежних версий нужно очистить данные приложения.
