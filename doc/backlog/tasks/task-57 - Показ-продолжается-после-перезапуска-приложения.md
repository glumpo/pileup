## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Ревью 2026-11-11 (doc/review-2026-11-11/reliability.md R2-02): сессия показа и стек экранов живут только в памяти. Если система убила процесс хоста (например, при запуске камеры), пересоздала Activity или ядро перезапущено после потери связи (TASK-48), показ и позиция теряются: ТВ стоит на последнем кадре, а новый показ начинается с первого файла.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Ядро: show.json в каталоге узла (device.WriteFile, атомарно): pile, экран (id, имя, вид, адрес), asset и taken_at курсора. Запись: при старте сразу, при смене курсора не чаще раза в 2 с (последний курсор дописывается при закрытии сессии); удаление — только при Stop (пользователь); Close ядра запись сохраняет.
2. Host.Interrupted (нет идущего показа и есть запись; pile нет — запись удаляется; удалённый файл — ближайший следующий по taken_at), Host.Forget; GET/DELETE /show/interrupted.
3. Host.Start: экран не найден обнаружением, но это экран записи (cast) — подключение по сохранённому адресу; неверный адрес = screen_unreachable.
4. Приложение: плашка на списке pile «Показ на «X» прервался.» [Продолжить] [Забыть]; ошибка экрана — причина и [Выбрать экран] (выбор экрана с тем же файлом). При старте ядра GET /show — идёт показ, открыть пульт. Пульт на no_show: если есть запись этого pile — продолжить сам один раз на каждое подключение к ядру (Api), иначе/при ошибке «Показ завершён…» с причиной, [Выбрать экран], [Закрыть].
5. Android: не останавливать ядро в OnActivityDestroys (только OnDestroy), CI android зелёный.
6. Тесты ядра/HTTP/jest, doc/adr, A63.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Находка R2-02 подтверждена чтением кода (show только в памяти, OnActivityDestroys → Mobile.stop, стек [piles]).
Решения: запись show.json в <Dir> (device.WriteFile, атомарно), а не таблица БД pile: показ один на узел, транзакция с данными pile не нужна. Запись при старте сразу, далее не чаще 2 с + досылка при закрытии сессии. Удалённый файл → первый с taken_at не раньше записанного. Подключение по сохранённому адресу добавлено (сразу после перезапуска ядра mDNS экран ещё не знает — без этого автопродолжение в ситуации 2 почти всегда давало бы unknown_screen).
Ситуация 2: пульт продолжает сам, один раз на каждый Api; неудача — «Показ завершён…» с причиной и «Выбрать экран».
Ситуация 3: Kotlin — удалён OnActivityDestroys { Mobile.stop() }, остаётся OnDestroy. App при старте ядра спрашивает GET /show.
Фикстура show.test: GET /show отвечает no_show до начала показа (как настоящее ядро), иначе тесты сразу открывали бы пульт.
Не проверено на устройстве: что Expo OnDestroy не срабатывает при пересоздании Activity и что после закрытия Activity назад ядро, работающее в фоне до смерти процесса, приемлемо.

CI на 1d5899f: check и android — success (ci-logs 79.1). Влит origin/master (TASK-58): конфликт только в architecture.md (A63/A64 — обе строки), session.go слился автоматически. После слияния: go test show/node/httpapi ok, tsc ok, jest 154/154 (один прогон под нагрузкой уронил существующий 'reconnecting to the screen for long…', три повтора зелёные — похоже на флак таймингов).
