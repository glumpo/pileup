## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
При последовательном просмотре следующий файл должен быть уже загружен, а прыжки по хронологии не должны ломать кеш. Правила зафиксированы в architecture.md, 6.2: окно из 20 элементов после курсора, дальше не грузим, вытеснение по самому раннему taken_at. Видео не предзагружается.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 После перехода курсора загружаются отсутствующие T2 из 20 следующих элементов в порядке хронологии; дальше окна загрузка не идёт
- [x] #2 При превышении бюджета первым вытесняется элемент с самым ранним taken_at; текущий файл, окно и закреплённые файлы не вытесняются
- [x] #3 С одного источника одновременно идёт не более 5 загрузок
- [x] #4 Файлы недоступного источника помечаются ожидающими, остальные файлы окна грузятся дальше, к ожидающим загрузка возвращается с повторами
- [x] #5 Логика покрыта тестами, включая прыжки вперёд и назад
<!-- AC:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Пакет core/prefetch: чистый планировщик без IO и реального времени. Состояние (кеш, закрепления, загрузки в полёте, отказы источников) внутри Cache, события — методами, решение — Plan(now) → что начать грузить и что вытеснить.
2. Окно: курсор + 20 следующих нескрытых элементов, загрузка по порядку хронологии, дальше окна ничего.
3. Вытеснение только сверх бюджета, по самому раннему taken_at; курсор, окно и закреплённые не трогаем.
4. Не более 5 загрузок с источника; недоступный источник — элементы «ждут», повтор с экспоненциальной задержкой и одной пробной загрузкой.
5. Тесты по спецификации (прыжки вперёд и назад) и property-тест на rapid по случайным последовательностям событий.
6. gofmt, go vet, go test -race, make check.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Начата чистая логика планировщика кеша; встраивание в показ — после TASK-12 и TASK-14.

Пакет core/prefetch: Cache — чистый планировщик без IO, горутин и реального времени (время передаётся в Plan/Failed). События: SetItems, SetCursor(id), SetBudget, Pin/Unpin, SetOnline, Loaded(id, size), Failed(id, now); решение: Plan(now) → (load, evict), Waiting() — ждущие элементы окна.
Решения: окно = элемент курсора (даже скрытый) + 20 следующих нескрытых; бюджет считается по фактическим размерам загруженных T2 (размер заранее неизвестен), загрузки в полёте не учитываются; окно грузится и сверх бюджета; если закреплённое и окно не влезают в бюджет — вытесняем всё остальное и остаёмся сверх бюджета; кешированные id, которых нет в хронологии, вытесняются первыми; при равном taken_at — по позиции в хронологии; загрузки, начатые до прыжка, не отменяются и занимают слоты источника.
Повторы: отказ загрузки делает источник недоступным; задержка 1, 2, 4, 8, 16, 30, 30… с (отказы во время уже идущей задержки её не увеличивают); после задержки — одна пробная загрузка, успешная загрузка с источника снимает отказ; переход источника offline→online сбрасывает задержку. Ждущие — незагруженные элементы окна недоступного (offline или с отказом) источника.
Тесты: prefetch_test.go (по спецификации, прыжки вперёд и назад), property_test.go (rapid, случайные события, инварианты окна, порядка, лимита, вытеснения, ожидания и повторов). Мутации проверены: тесты ловят изменение окна, лимита, пробы, порядка и минимальности вытеснения, защиты курсора, пропуска скрытых, сброса отказа, предела задержки.

Проверка владельцем: тесты (включая -race) проходят; влито в master (8a2537d). Решение A15 записано. Критерии выполнены на уровне логики; задача остаётся In Progress до встраивания в сессию показа (TASK-14/TASK-16).
Риск для TASK-16: файл, который постоянно не грузится с рабочего источника (например, 404), блокирует этот источник — пробная загрузка всегда выбирает самый ранний недостающий элемент.

Встроено в сессию показа (core/show, коммит 4749140): SetItems из хронологии хоста (id элемента = asset/revision, источник = владелец), Loaded для T2, уже лежащих в blob-хранилище (проверка только для новых элементов), SetOnline по живому исходящему pull-соединению с владельцем (node.Online: announce прошёл, Pull ещё не вернулся), Plan после старта, каждого шага курсора, каждой завершённой загрузки и раз в секунду (тик даёт и повторы по задержке планировщика); load → node.Blob(T2) с владельца или рендер своего, evict → node.Evict (удаляет ссылку и blob; ссылка на удалённый blob считается отсутствующей). Ждущие элементы окна — в состоянии сессии (waiting).
Тесты core/show: окно T2 загружено до запроса экрана и дальше окна ничего (источник рендерит каждый T2 ровно раз), после прыжка — новое окно; вытеснение до бюджета самых ранних (P00–P04 из 30 при бюджете 25 файлов), T1 не трогается; файлы выключенного источника ждут, остальные грузятся, после возвращения источника догружаются.
Риски: постоянная ошибка одного файла (404) по-прежнему блокирует источник; вытеснение файла, удалённого из pile, не удаляет его blob; если announce к источнику не проходит, а pull работает, источник считается офлайн.
