## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Проверка утверждений R15 по коду ветки task-21:
- Подтверждено: commit писал selection.json и p.local до операций, а AssetRemove и AssetAdd создавались отдельными транзакциями. Сбой или ошибка между шагами оставляли новый диапазон и соответствие при старом или наполовину изменённом журнале; при запуске соответствие бралось из файла, прерванное изменение не завершалось.
- Подтверждено с уточнением: готовые T1/T2 выдаются по записи журнала (Valid проверяет текущие asset/revision раньше, чем используется соответствие). Для кеша это правильно: журнал — источник истины опубликованного. Ошибкой было расхождение журнала с выбором: исключённый файл после сбоя оставался опубликованным и отдавался из кеша, а для файла, оставшегося в журнале без соответствия, рендер и T3 давали ErrUnknownAsset. Соответствие не может указывать на другой файл, так как asset_id = SHA-256(pubkey ‖ local_id); оно может только отсутствовать. После общей транзакции расхождение невозможно.
- Устарело для task-21: строки таблицы ревью про pins.json и refs — уже перенесены в blobs/cache.db (TASK-21).
- Технического обоснования отдельного файла в A17/A18 нет, подтверждено; «JSON проще для gomobile» относится к MediaProvider.

Красные тесты на прежнем коде (28a5f95, e1ac460):
- TestInterruptedSelectionChangeIsAllOrNothing/crash_after_the_selection_is_written,_before_the_first_op: после перезапуска диапазон новый, журнал старый; файл 1 опубликован, но не отдаётся (502).
- TestInterruptedSelectionChangeIsAllOrNothing/crash_between_the_ops: диапазон новый, AssetRemove записан, AssetAdd нет.
- TestFailedSelectionChangeLeavesPreviousSelection: после ошибки записи второй операции и в памяти, и после перезапуска новый диапазон при половинном журнале.
- TestSelectionOfPreviousVersionIsKept: «previous selection file is still there».
- Подтесты «сбой при подготовке» и «сразу после возврата изменения» зелёные и на прежнем коде: там граница до первой записи и после последней тоже соблюдалась.
- TestClosedNodeLeavesNoRequestsRunning: «store of a closed node: database is locked (5) (SQLITE_BUSY)» на 4–8 раунде из 20.
Точки отказа без sleep: триггер SQLite BEFORE INSERT ON ops на N-ю новую операцию. В дочернем процессе он вызывает зарегистрированную функцию с os.Exit (аварийное завершение посреди транзакции), в процессе теста — RAISE(ABORT) (ошибка записи). Сбой при подготовке — os.Exit внутри MediaProvider, сбой после commit — os.Exit сразу после возврата Select.

Решение (4cee641; остановка узла — 830e813, bc3809e):
- В piles/<id>.db локальные таблицы selection (range_from, range_to; одна строка), decisions (asset_id, selected), files (asset_id, local_id). Они не реплицируются: протокол передаёт только ops.
- store.Select(key, wallTime, selection, changes...) — одна транзакция: сначала выбор, затем каждая операция как Create (seq, L, проекция). replica.Select ждёт догрузки собственного журнала так же, как Create (R08), и уведомляет подписчиков после commit.
- Подготовка (MediaProvider, taken_at, разница с опубликованным) выполняется до транзакции под n.selecting. AssetRemove и AssetAdd остаются отдельными подписанными операциями.
- p.local удалён: local_id читается из БД (store.LocalID) при рендере и T3. Копии в памяти нет, поэтому обновлять после commit нечего; T1/T2, T3 и журнал согласованы одной транзакцией.
- Перенос: при открытии pile существующий selection.json импортируется одной транзакцией (замещает выбор в БД) и удаляется. Сбой между импортом и удалением ведёт к повторному импорту того же содержимого. В файл больше никто не пишет.

Флейк TestChangingRangePublishesOnlyTheDifference: http.Server.Close не ждёт обработчиков, а database/sql DB.Close закрывает только свободные соединения. Соединение SQLite, занятое обработчиком пира (например, /vv), закрывалось уже после Node.Close, с checkpoint WAL, параллельно с открытием файла в тесте — SQLITE_BUSY. Исправление: контекст запросов — контекст узла (BaseContext); обработчики учитываются в n.wg (Add под n.mu с проверкой отмены, как addPeer → pull); Close отменяет контекст под n.mu, ждёт n.wg, затем закрывает blob-кеш и хранилища. Запрос, пришедший после отмены, обрывается (http.ErrAbortHandler): клиент видит недоступность, а не отказ владельца (503 давал ErrRefused, и показ считал файл сломанным). Сам тест не менялся.

Инвентаризация постоянного состояния и границы атомарности:
| Данные | Где | Почему там | Атомарность и восстановление |
| --- | --- | --- | --- |
| Журнал ops, проекция (pile, members, claims) | piles/<id>.db | A9: одна БД на pile | Каждая операция — транзакция с seq/L/проекцией |
| Диапазон, ручные решения, asset_id → local_id | piles/<id>.db: selection, decisions, files (не реплицируются) | Должны меняться вместе с AssetRemove/AssetAdd своего pile | Одна транзакция с операциями; копии в памяти нет |
| piles.json: id, секрет, порт, адреса пиров | каталог данных узла | Индекс pile: нужен до открытия БД pile (путь и секрет для валидатора), общий для узла | Запись tmp + fsync + rename. Create/Join: сначала БД pile с операциями, затем piles.json. Сбой между ними оставляет БД без записи: при Create — неиспользуемый файл (приглашение ещё не выдано), при Join — повторный вход тем же приглашением открывает ту же БД (путь по pile_id) и продолжает журнал, форка нет. Потеря адреса пира восстанавливается через announce/mDNS, потеря порта — новым портом и announce. Общей транзакции с БД pile перенос в SQLite не даёт (это другой файл), поэтому piles.json не переносится |
| objects, holds, pins | blobs/cache.db (TASK-21) | Кеш общий для узла: один файл может удерживаться несколькими pile; pins решают вытеснение в той же БД | Транзакции cache.db; с журналом pile общей транзакции не нужно: кеш производный, Valid перепроверяет журнал перед публикацией, Retain снимает удержания удалённых и старых ревизий |
| Файлы blob | blobs/<sha256> | Содержимое вне БД | rename до вставки строки; при открытии удаляются файлы без строк и строки без файлов |
| Временные файлы | blobs/tmp/ (загрузки), *.tmp от device.WriteFile | — | blobs/tmp очищается при открытии; *.tmp перезаписывается при следующей записи и не читается |
| Ключ устройства | Keystore: Android — seed, зашифрованный ключом AndroidKeyStore, в noBackupFilesDir/device.seed (A21); iOS — Keychain; десктоп и тесты — device.File | Защищённое хранилище, вне бэкапа: восстановленное устройство — новый автор; нужен до открытия любых pile | Создаётся один раз до всего остального; Save атомарен (tmp + rename) |
| Старые pins.json, selection.json, refs/ | — | Переносятся и удаляются при открытии | Импорт одной транзакцией, затем удаление; повтор идемпотентен |
Только в памяти, восстанавливать не нужно: счётчики онлайн и найденные mDNS-сервисы, кольцо диагностики, окно показа (Protect), попытки загрузки blob, состояние догрузки replica, сеансы показа и экранов, набор неудавшихся thumbhash до перезапуска (A19).

Решения для architecture.md: A17/A18 — выбор и соответствие asset_id → local_id хранятся в локальных таблицах БД pile и меняются одной транзакцией с AssetRemove/AssetAdd; selection.json переносится и удаляется. A16 — piles.json остаётся файлом (обоснование выше). Node.Close дожидается обработчиков запросов пиров.

Риски и не сделано:
- selection.json, уже расходящийся с журналом после прежнего сбоя, переносится как есть; журнал выравнивается следующим Select/Decide, до этого рендер и T3 файла без соответствия дают ErrUnknownAsset.
- Остаток selection.json.tmp от прежней версии не удаляется (не читается).
- Редактирование файла без повторного выбора: рендер по local_id даёт новое содержимое под старой revision — это R16.
- device.WriteFile не синхронизирует каталог после rename: при отключении питания piles.json может откатиться к предыдущей версии (последствия те же, что у сбоя между созданием БД и записью piles.json).
- mobile.Stop закрывает UI-сервер (httpapi) через Close, тоже не дожидаясь обработчиков, и сразу закрывает узел; быстрый Start на том же каталоге может получить тот же SQLITE_BUSY. В этой задаче не исправлялось.
